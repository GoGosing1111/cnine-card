PATCH NOTES v1901 — 모바일 "앗, 이런!" (크롬 렌더러 OOM) 수정
===============================================================================

■ 제보
  모바일 유저들이 몬스터 토벌 전투 화면에서
    1) 전장이 흰 화면으로 남고 헤더가 "SERVER ASSET SYNC" 에서 멈춤 + 깨진 이미지 아이콘
    2) 이어서 크롬 "앗, 이런! 이 웹페이지를 표시하는 도중 문제가 발생했습니다"
  를 자주 본다.

  (2)는 크롬 렌더러 프로세스가 죽었을 때 나오는 화면이다(영문 "Aw, Snap!",
  대부분 SBOX_FATAL_MEMORY_EXCEEDED = 메모리 초과). (1)은 그 직전 단계로,
  메모리가 말라 이미지 디코딩과 텍스처 업로드가 실패한 상태다.
  즉 전투 로직 버그가 아니라 V3 전투 화면의 메모리 누적 문제다.

■ 원인 1 — Pixi Assets 캐시가 한 번도 해제되지 않았다
===============================================================================
  preview/project-v-v3/source/battle/ 전체에 Assets.unload() 가 한 곳도 없었다.
  Pixi 의 Assets 캐시는 URL 단위 영구 보관이고, 이 앱은 SPA/PWA 라 페이지가
  새로고침되지 않는다. 게다가 battle-v3-live.js 는 window.__V3_PIXI_MOUNTED 로
  Application 을 세션 내내 살려 두고, renderer.destroy() 는 setVisible(false) 만 한다.

  => 한 세션 동안 싸운 모든 카드/몬스터 텍스처가 전부 렌더러 메모리에 남았다.
     자동전투·무한의탑처럼 판을 반복할수록 단조 증가한다.

  [수정] BattleEngine 에 판 단위 자산 수명 관리를 넣었다.
    - trackLiveAssetPreload(preloadUrls, artEntries)
        이번 판이 쓰는 URL -> Texture 를 Map 으로 기록한다.
        loadBattleArtTexture 의 PNG 폴백 URL 도 "쓰는 중"으로 함께 잡는다.
    - releaseStaleLiveAssets()
        지난 판 Map 과 이번 판 Map 을 비교해, 더 이상 안 쓰는 URL 만 unload 한다.
        unload 전에 characters 의 texture / fullBodySprite.texture / cutInTexture 와
        objectiveSprite.texture 중 해당 텍스처를 가리키는 참조를 Texture.EMPTY 로
        먼저 끊는다. (파괴된 텍스처가 스프라이트에 물려 있으면 다음 프레임에서
        렌더가 통째로 실패해서 정확히 제보된 "흰 화면"이 된다.)
    - setBattlePayload() 는 얇은 래퍼가 되고 본문은 applyBattlePayload() 로 옮겼다.
      래퍼의 finally 에서 회수를 돌리므로, 본문 중간의 early return 경로에서도
      반드시 실행된다.

  ※ 번들 정적 자산(ASSETS/BUNDLE)과 전장 배경은 애초에 추적 대상이 아니라
    절대 해제되지 않는다. 회수 대상은 "판마다 바뀌는 카드/몬스터 아트"뿐이다.

■ 원인 2 — 컷인용 원본 카드 아트만 다운스케일을 피해 갔다
===============================================================================
  v1803 이 전투 스프라이트를 384px 변형으로 돌릴 때 대상은 battle-v3-live.js 의
  SPRITE_URL_KEYS 뿐이었다:
      image / imageBattle / battleImage / imageUrl / image_url / primaryUrl / pngFallbackUrl

  그런데 BattleEngine.originalCardArtUrl() 이 컷인용으로 고르는 후보는
      sourceArtUrl / sourceArt / source_art / originalCardArt /
      imageOriginal / cardImage / image_url_original
  이고, 이 키들은 위 목록에 없다. 그래서 한 판마다 카드 최대 10장의 **원본 카드 아트**
  (평균 334KB, 디코딩하면 대략 1024x1445x4 = 장당 5~6MB)를 그대로 캐시에 넣었다.
  원인 1과 곱해지면서 이번 증상의 가장 큰 지분을 차지한다.

  [수정] cutInVariantUrl() 추가.
    후보 "선택"은 지금처럼 원본 경로로 비교하고(스프라이트와 같은 그림을 컷인에
    넣지 않기 위한 기존 로직 유지), 실제로 받는 URL 만 cnineBattleSpriteUrl(url, 384)
    으로 바꾼다. 매핑이 없는 이미지는 원본 그대로 통과한다.
    컷인은 화면에서 최대 반 폭이라 384 변형으로 화질 손실이 없다.
    장당 5~6MB -> 약 0.83MB (약 7배 절감).

■ 원인 3 — 모바일에서도 렌더러 예산이 데스크톱과 같았다
===============================================================================
  mount() 가 항상 antialias:true, resolution:min(devicePixelRatio,2) 로 초기화했다.
  캔버스 백버퍼와 MSAA 리졸브 버퍼는 GPU 가 아니라 렌더러 프로세스 메모리에 잡힌다.
  DPR 3 단말에서는 이것만으로 고정 수십 MB 다.

  [수정] LOW_MEMORY_DEVICE 판정 추가
    navigator.deviceMemory <= 4  또는  (max-width:860px) / (pointer:coarse)
      -> antialias:false, resolution:min(devicePixelRatio,1.5)
    데스크톱은 종전 그대로(antialias:true, resolution 2).
    SD 스프라이트는 화면에서 60~110px 로 그려지므로 육안 차이가 없다.

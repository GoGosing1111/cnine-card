# 폐차장 원정 결과 정산·응답 복구

## 운영에서 확인한 원인

2026-09-23 운영 Neon을 읽기 전용으로 확인했다. 완료 원정 46,947건과 PREPARED 원정 25건이 있었고, 미완료 25건의 오류는 모두 `unified_drop_ledger_v1667.pool_id` NOT NULL 위반이었다. 보호권 출시 이후 당첨된 `EQUIPMENT_PROTECTION_TICKET`은 승인된 별도 게임 보상이므로 poolId/entryId가 null인데, 일반 통합 드롭 원장에 넣으면서 정산 트랜잭션이 매번 롤백됐다. 입장권 예약과 전투·보상 스냅샷은 보존돼 있었다.

## 수정

- 승인 정책과 보호권 출처 검증을 먼저 수행한다. 해당 보호권만 풀 전용 원장 대상에서 제외하고, 실제 지급과 인벤토리 원장 및 원정 완료 영수증은 같은 트랜잭션에 유지한다. 일반 부품의 풀 원장은 그대로 기록한다. 임의의 풀 ID나 빈 원장 값을 만들지 않는다.
- 기존 PREPARED 요청은 원래 전투·보상 계획으로 정산한다. 입장권 재차감, 보상 재추첨, 정책·확률 변경이 없다.
- 통신 오류·503·계정 잠금 이후에는 동일 요청의 결과 GET을 먼저 확인한다. 활성 처리 임대가 끝나기 전에는 조회로 기다리고, 재개 가능 시에만 같은 요청을 POST한다. 재시도 시간과 연속 통신 실패 횟수는 제한한다.
- 폐차장 재진입 시 브라우저에 남은 요청 또는 서버의 진행 중 요청을 자동 복구한다. 계정·화면 변경 시 추가 요청을 멈추며, 확인 전 요청번호를 지우지 않는다.
- 완료된 영수증을 받은 뒤 전투 표시가 실패하면 저장된 결과 화면을 표시한다.
- 앱과 폐차장 스크립트 캐시 쿼리 `scrapRecovery=20260923`을 추가한다. 기존 서비스워커의 network-first 대상은 유지한다.

## 검증

- 서버 33개 통과: SQLite와 PostgreSQL에서 일반 부품+보호권 동시 지급, 중간 실패 전체 롤백, 설정 변경 뒤 저장된 결과 복구, 재시도 시 입장권·코인·부품·보호권 중복 처리 방지를 검증했다.
- 클라이언트 8개 통과: 완료 응답 유실, 접수 전 503, 잠금 거절, 긴 임대 대기, 서버 원본 요청 발견, 새로고침 후 결과 조회, 화면 전환 취소, 영구 장애의 제한된 재시도를 검증했다.
- 실제 앱과 V3 렌더러를 격리 SQLite 계정에 연결했다. 데스크톱 1440px에서 커밋 후 응답을 503으로 잃어도 POST 1회·결과 GET 1회로 전투와 결과 화면까지 이어졌다. 모바일 390px에서는 정산 실패 후 새로고침·폐차장 재진입으로 원래 결과가 복구됐다. 두 원정 합계 입장권 5→3, 보호권 0→2, 완료 영수증 2건, 브라우저 예외·알림창 0건이었다. 모바일 결과의 보상·복귀 버튼과 가로 넘침 없음, 데스크톱 실제 전투를 직접 시각 확인했다.
- 재현 서버: `JOINT_QA_NATIVE=1`, `JOINT_QA_SCRAPYARD_RECOVERY=1`, `JOINT_QA_PORT=8974`로 `node scripts/serve-joint-account-qa.mjs` 실행. `/__qa/scrapyard-recovery`에서 격리 원장 조회 및 `loseNextResponse`, `failSettlement` 장애 주입. 이 경로는 로컬 QA 서버에만 존재한다.
- 캡처·브라우저 보고서: `C:/Users/User/AppData/Local/Temp/cnine-scrapyard-recovery-20260923/`.

## 배포

깨끗한 범위 커밋에서 정규 `npm run deploy:production`을 실행한다. 내장 `npm run release:gate`와 Hyperdrive 캐시 OFF 검사 통과가 필수다. 운영 계정 잔액·입장권·영수증을 수동 편집하거나 신규 원정을 대신 시작하지 않는다. 기존 원정은 동일한 서버 정산 경로로 복구한다.

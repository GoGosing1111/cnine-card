# 붕괴 코어 봉인 선택 보상

2026-09-25 사용자 지시: 클리어 후 봉인된 보상 3개 중 하나를 선택해 공개한다. 기존 100억 코인은 유지하고 선택 보상을 추가한다. 최소 지급량은 운영자가 CMS에서 직접 정한다.

같은 날 후속: 사용자가 CMS 내용을 저장하고 V2 연출의 게임 연결을 승인했다. 운영 조회에서 선택 보상 ON, 리비전 2, 최소 마스터의 별 50,000개(가중치 100), 사용 후보 3개를 확인했다. 이 설정은 재배포로 덮어쓰지 않는다. V2 연결과 이번 주 전체 유저 보상 횟수 일회 초기화는 `docs/core-raid-reward-v2-release-20260925.md`를 따른다. 아래 최초 OFF 기록은 초기 배포 시점의 상태다.

## 운영 설정

- CMS → 레이드 → **붕괴 코어 · 선택 보상**에서 독립적으로 설정한다. 기존 붕괴 코어 전투/기본 보상 설정과 다른 저장 문서다.
- 최초 상태는 OFF, 최소 수량 미입력이다. 배포·조회는 운영 설정을 자동 생성하거나 바꾸지 않는다. 최소 코인 또는 마스터의 별의 양과 가중치를 입력한 뒤 추가 보상을 ON으로 저장한다.
- 지원 후보: 용병, 장비, 아이템/재료, 코인, 마스터의 별, 카드 조각, 마력 결정. 명시적으로 추가하고 사용 체크한 후보만 추첨한다. 새 용병·재료가 출시돼도 자동 편입하지 않는다.
- 최소 보상도 가중치 추첨에 포함된다. 3개는 독립적으로 추첨하며 같은 내용이 나올 수 있다. 빈 보상, 0 수량, 음수·소수·무한 값은 저장할 수 없다. 코인/마별 후보는 동일 재화의 최소 수량보다 적게 설정할 수 없다.
- 장비보호권의 승인된 획득 경로를 우회하지 않으며 이 목록에서 제외한다. 용병 원화와 기존 V3 전장/카드 도크는 변경하지 않는다.
- 기존 100억 코인, 조각 설정, 피그 코인 지급 및 주간 보상 3회 규칙을 유지한다. 한 번 수령하면 기본·추가 보상 모두 정산되어 주간 1회를 사용한다.
- ON/OFF와 후보 변경은 새 봉인부터 적용한다. 이미 열린 봉인의 내용과 선택은 보존한다. 긴급 전체 정산 중지는 기존 레이드 보상 잠금을 사용한다.

## 정산과 복구

- `app_meta.raid_core_choice_rewards_v1`: 별도 설정. OWNER 및 동일 출처 검증, 리비전 CAS, 요청 ID 재사용 시 동일 내용 확인. 설정 변경 전후 기록을 같은 트랜잭션에 보관한다.
- 기존 `raid_core_receipts_v2024`의 예약된 `CORE-CHOICE-` / `CORE-CONFIG-` ID를 사용한다. 공대/계정에 대한 SHA-256 식별자 하나로 보상 봉인을 고정하며 일반 OPEN/RESOLVE 경로에서 해당 비공개 영수증을 읽을 수 없다.
- `/api/raid/core/rewards/open`: 참가·CLEAR·보상 잠금·주간 자격 검증 후 3개의 슬롯 번호만 반환한다. 지급 전에는 내용이 브라우저에 전송되지 않는다. 완료 영수증이 있으면 지급 결과만 다시 읽는다.
- `/api/raid/core/claim`: 첫 선택을 CAS로 고정하고 기존 주간 정산에 추가 지급을 포함한다. 동일 계정·공대는 한 번만 지급한다. 주간 예약 상실 시 추가 지급 전에 원자성 가드가 실패하여 거래 전체를 되돌린다.
- 장비 `INSERT ... SELECT` 지급 행수가 0이면 기본 코인·주간 횟수·피그 코인까지 롤백한다. 선택은 유지한다. 후보가 비활성화됐다면 처음 봉인할 때 저장한 최소 보상으로 전환한다. 최소 보상 자체를 지급할 수 없으면 0 지급으로 완료하지 않고 재시도 상태로 남긴다.
- 요청·모듈 로드·후속 조회는 15초 제한으로 무한 대기를 막는다. 재접속 시 서버의 선택을 복원하고 재시도한다. 보상 결과는 지급 완료 영수증에서만 표시한다.
- 선택 UI/CMS는 지연 로드한다. 전황의 5초 폴링에 후보 조회나 원화 프리로드를 추가하지 않는다. 공용 GSAP 벤더는 선택 연출 보강에만 사용하고 로딩 실패가 지급을 막지 않는다.

## 검수와 배포 범위

- SQLite/PostgreSQL 신규 16개 검사: 최소 보상/가중치 검증, OWNER/CAS/동일 요청, 비공개 봉인, 설정 변경 후 보존, 7개 지급 유형, 용병 중복 누적, 잔액 로그, 지급 실패/응답 유실, 장비 0행 롤백, 최소 보상 대체, 동시 마지막 주간 횟수, 기존 OFF 경로 및 캐시 연결.
- 개발 중 기존 코어 레이드/주간 보상 관련 35개 검사도 통과했다. 전체 배포 게이트를 별도 중복 실행하지 않는다.
- 실제 Chrome 1440×1000 / 390×844에서 본게임 코어 모듈과 실제 서버 핸들러를 격리 SQLite에 연결해 선택·공개·받은 보상 재확인, CMS 검색/후보 추가/수량/가중치 저장을 확인했다. 모바일에서는 지급 실패 후 새로고침·선택 복구·동일 보상 재시도를 확인했다. 가로 넘침/페이지 오류 없음.
- 로컬 검수 수량(최소 마별 2/7개, 용병 1장)과 ON 설정은 테스트 DB 전용이다. 운영에 저장하지 않는다. `node tests/serve-core-rewards-qa.mjs`로 루프백 검수를 재현할 수 있다. 화면 증빙은 배포 루트 밖 `../qa-core-rewards/`에 보존한다.
- 직전 운영 배포는 Cloudflare 목록의 `3e94b425-7071-400d-9c02-8e761a35a250`, 소스 `abf8d0898e9e4af04c8562387ac3ab0d8bf38a0c`로 확인했다.
- 변경 영향은 붕괴 코어 보상/CMS/결과 UI로 한정된다. 기존 공통 DB·트랜잭션·인증 기반, 스키마, 의존성, 전투는 변경하지 않는다. `docs/scoped-release-policy-20260923.md`에 따라 scoped 배포에서 `test:core-raid`와 `check:worker`, 출시/캐시/Hyperdrive 검사를 수행한다. 신규 보상 검사는 `test:core-raid`에 포함했다.
- 지정 배포 명령: `npm run deploy:production -- --scoped`. 배포 후에는 변경 파일과 새 API 권한 경로만 짧게 확인한다. 운영 보상 지급 테스트는 수행하지 않는다.

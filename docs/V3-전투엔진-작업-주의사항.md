# V3 전투엔진 작업 주의사항

2026-08-22 ~ 08-23 사이에 실제로 터졌던 것들을 정리했습니다.
추측이 아니라 **전부 이 기간에 직접 겪고 고친 것**입니다.

---

## 0. 가장 먼저 — V2와 V3의 역할

```
V2  전투 결과를 정한다 (승패 · 데미지 · 보상)
V3  그 결과를 연출한다 (애니메이션 · 이펙트 · 사운드)
```

**밸런스가 이상하면 V3를 봐도 소용없습니다.** V3는 이미 정해진 결과를 그리기만 합니다.
반대로 연출만 고치려는데 V2를 건드리면 실제 전투 결과가 바뀝니다.

이걸 헷갈려서 보스 밸런스 버그를 한참 늦게 잡았습니다.

---

## 1. ⚠ 전투 경로가 **둘**이다 — 가장 많이 당하는 함정

| 경로 | 위치 | 용도 |
|---|---|---|
| `resolveAutoBattle()` | `[[path]].js` 약 1390행 | 자동사냥 |
| `path==='battle/fight'` | `[[path]].js` 약 5639행 | 수동 전투 |

**수동 전투는 `resolveAutoBattle` 을 호출하지 않습니다.** 로직이 통째로 복사돼 있습니다.
확인해 보면 `battle/fight` 블록 안에 `bossUltimate` 관련 코드가 22곳 따로 있습니다.

### 실제 사고

보스 궁극기 피해가 개별 설정값 대신 상한값(150%)으로 적용되던 버그를 고칠 때,
`resolveAutoBattle` 만 고치고 배포했습니다. **자동사냥은 정상이 됐는데 수동 전투는 그대로였습니다.**
유저 제보를 두 번 받고서야 두 번째 경로를 찾았습니다.

```js
// 두 곳 모두 이 형태여야 한다
const bossUltimateCap = Math.max(0, Number(difficulty.bossUltimateCapPercent ?? 100) || 0);
const bossConfigured  = Math.max(0, Number(monster.ultimate_pve_damage_percent
                                        ?? monster.ultimate_damage_percent ?? 0) || 0);
const bossPveDamagePercent = Math.min(bossUltimateCap, bossConfigured);   // 상한은 상한으로만
```

### 규칙

> **전투 밸런스를 건드리면 반드시 두 경로 다 고치고, 두 경로 다 테스트한다.**
> 무한의탑(`ultimate_tower_damage_percent`)까지 세 번째 경로가 있는 항목도 있습니다.

보상 지급도 비대칭입니다 — `battle/fight` 는 보상 6종을 `Promise.all` 로 병렬 처리하는데
`resolveAutoBattle` 은 아직 순차입니다. 한쪽만 고치면 체감 속도가 갈립니다.

## 2. ⚠ DB가 D1(SQLite) → PostgreSQL 로 바뀌었다

**2026-08-23 새벽에 이관했습니다.** SQLite에서 되던 문법이 Postgres에서 거부됩니다.
호환 계층(`functions/_postgres_d1_compat.js`)이 상당수 번역하지만 **전부는 아닙니다.**

### 이미 터진 것 (호환 계층에서 처리하도록 고쳐둠)

**① `ON CONFLICT ... DO UPDATE SET` 안의 한정 없는 컬럼**

```sql
-- SQLite: 통과   /   Postgres: ERROR column reference "quantity" is ambiguous
ON CONFLICT(user_id,item_code) DO UPDATE SET quantity=quantity+1

-- 올바른 형태 (우변만 한정, 좌변은 한정하면 안 됨)
ON CONFLICT(user_id,item_code) DO UPDATE SET quantity=cnine_user_inventory.quantity+1
```

코드에 `ON CONFLICT DO UPDATE` 가 **71곳**, 그중 18곳이 한정 없이 쓰고 있었습니다.
프리미엄 큐브(`quantity`), 마법카드(`user_id`), 장비 보급상자가 이걸로 죽었습니다.

**② 단항 마이너스 + 바인딩 파라미터**

```sql
-- SQLite: 통과   /   Postgres: ERROR operator is not unique: - unknown
SELECT ?,?,-?,quantity,... FROM cnine_user_inventory

-- 호환 계층이 (0-$3) 으로 바꿔줍니다. 이항 마이너스(quantity-?)는 그대로 둡니다.
```

### 새로 쓸 때 지킬 것

| SQLite 습관 | Postgres에서 |
|---|---|
| `datetime('now','-30 days')` | 문자열 시각 비교라면 `to_char(now() AT TIME ZONE 'UTC' - interval '30 days','YYYY-MM-DD HH24:MI:SS')` |
| `INSERT OR IGNORE` | `ON CONFLICT DO NOTHING` (호환 계층이 처리) |
| `INSERT OR REPLACE` | `ON CONFLICT(키) DO UPDATE` — **동작이 다릅니다.** SQLite는 행을 지우고 다시 넣어 명시 안 한 컬럼이 초기화되지만, Postgres는 명시한 것만 바꿉니다 |
| `MIN(a,b)` 스칼라 | `LEAST(a,b)` (호환 계층이 처리) |
| `json_each(?)` | `jsonb_array_elements_text($1::jsonb)` |
| `RANDOM()` | `random()` — SQLite는 **64비트 정수**, Postgres는 **0~1 실수**. 값을 쓰면 반드시 변환 |

**시각 컬럼은 여전히 TEXT 입니다** (`'2026-08-23 02:45:00'`). timestamptz 로 바꾸지 마세요.
문자열 비교하는 코드가 수백 곳이라 동시에 다 깨집니다.

### 성능 모델이 바뀌었다

```
D1        쿼리를 한 번에 하나씩 → 동시 요청이 몰리면 22배 느려짐
Postgres  동시 처리 → 동시 30개에서도 응답이 거의 안 늘어남 (실측)
```

**단, 요청 1건당 DB 연결을 새로 엽니다.** 그 고정비용이 약 235ms입니다
(`/api/health` 는 쿼리가 0개인데도 264ms, 정적 파일은 29ms).

> 그래서 **순차 쿼리 개수는 여전히 줄일 가치가 있습니다.** 왕복이 곧 지연입니다.
> `env.DB.batch([...])` 로 묶을 수 있으면 묶으세요.

### Advisory lock 은 못 씁니다

Hyperdrive를 거치면 `LISTEN/NOTIFY`, `PREPARE/EXECUTE`, **advisory lock** 이 막힙니다.
"Postgres 왔으니 advisory lock 쓰면 되겠다" 는 길은 없습니다.
**유저 뮤테이션 락은 Durable Object(`USER_LOCK`)를 그대로 유지해야 합니다.**

## 3. 멱등성 영수증 — 실패하면 유저가 갇힌다

전투·뽑기·진화는 `requestId` 기반 영수증으로 중복 실행을 막습니다.

**문제**: 영수증을 먼저 쓰고 작업이 중간에 실패하면, 재시도 때 "이미 처리된 요청입니다" 로
막혀서 **유저가 영구히 갇힙니다.** 실제로 Postgres 이관 직후 진화에서 이게 터졌습니다.

```
진화 처리에 실패했습니다.
이미 처리된 진화 요청입니다.
```

### 규칙

- 새 쓰기 경로를 만들면 **영수증은 성공 후에 확정**하거나, 실패 시 정리 경로를 반드시 넣을 것
- 자산(코인·카드·별)을 소모하기 **전에** 실패할 수 있는 구간을 앞으로 몰 것
- 배포 후 `PENDING` 으로 굳은 영수증이 없는지 확인할 것

## 4. 스프라이트 · 텍스처

### 반응형 이미지 맵에 없으면 404 입니다 (폴백 없음)

```js
window.CNineResponsiveBattleSprites   // SD 스프라이트 86종
window.CNineResponsiveCardImages      // 카드 이미지 337종
```

`assetUrl()` 이 `window.cnineBattleSpriteUrl` 을 거쳐 축소본 경로로 바꿉니다.
**맵에 없는 새 에셋을 추가하면 원본으로 안 떨어지고 그냥 404 납니다.**
새 스프라이트를 넣으면 맵과 실제 파일을 **같이** 넣어야 합니다.

### payload 재작성 대상이 정해져 있다

`battle-v3-live.js` 의 `rewriteBattleSpriteUrls(payload)` 는 이 셋만 훑습니다.

```js
battleV2.teams[*].cards      // 양 팀 카드
cards                        // 카드 배열
monster                      // 몬스터
```

**타임라인은 안 봅니다.** 연출 데이터에 새로 이미지 필드를 넣으면 축소본이 적용되지 않습니다.
필드를 추가하면 `rewriteSpriteCard` 대상도 같이 늘려야 합니다.

### PixiJS v8 텍스처는 자동으로 안 풀린다

```js
container.destroy({ children: true });   // ← 텍스처는 그대로 남습니다
```

전투를 연속으로 돌리면 그래픽 메모리가 쌓여서, 저사양 기기에서 전장이 다시 구성되거나
화면이 깨집니다. 텍스처는 별도로 해제해야 합니다.

크기 기준: `BattleCharacter.js` 높이 384 × scale 0.48 ≈ **화면 184px**.
원본 1,300px을 그대로 쓰면 7배를 낭비합니다.

## 5. 클라이언트 캐시 버스트

클라이언트 JS를 고치면 **반드시 `?v=` 를 올려야 합니다.** 서비스워커가 `SHELL_CACHE` 에
담아두기 때문에, 안 올리면 유저는 옛 파일을 계속 씁니다.

```html
<script src="js/app.js?v=1803i-timer-stop"></script>
```

`index.html` 과 `service-worker.js` 양쪽을 확인하세요. 서버(`functions/`)만 고쳤다면
버전을 올릴 필요가 없습니다.

## 6. 검증 방법 — 이게 버그를 잡았습니다

전투 로직은 **실제 소스에서 함수를 그대로 뽑아 가짜 env 위에서 돌려** 확인했습니다.
재구현해서 테스트하면 진짜 코드의 버그를 못 잡습니다.

```js
const src = fs.readFileSync('functions/api/[[path]].js', 'utf8');
const block = src.slice(src.indexOf('function drawOneFromContext'), ...);
const fn = new Function(`${block}\nreturn drawOneFromContext;`)();
// 가짜 env 로 수천 번 돌려 분포를 본다
```

보스 밸런스 버그는 이 방식으로 **같은 덱에서 5번째 카드만 바꿔 40회씩** 돌려서 증명했습니다.

```
수정 전   리미티드13강 65,904  /  FUR11강 40,277   ← 강화했는데 더 약함
수정 후   리미티드13강 117,364 /  FUR11강 125,903 /  FUR13강 154,227
```

SQL을 고칠 때는 **실제 PostgreSQL을 띄워서** 확인하세요. 컨테이너에 `postgresql-16` 이
들어 있습니다. 추측으로 넘어가면 스키마 변환기가 `NOT NULL` 을 통째로 날려먹는 것 같은
사고가 납니다(실제로 한 번 그랬고, 실행해봐서 잡았습니다).

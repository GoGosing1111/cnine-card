# 장비창 로딩 최적화 — 2026-09-18

## 원인과 운영 DB 실측

- `user_equipment_instances`는 조사 시 약 1억 6,269만 행이었다. 계정별 장비 수량과 `MAX(acquired_at)`를 한꺼번에 집계하면서 PostgreSQL이 전체 테이블 병렬 순차 스캔을 선택했다.
- 딤럼프 계정의 기존 장비 핸들러는 12,581ms, 그중 장비 집계는 8,999ms였다. 하이희야 계정은 기존 집계가 15초 제한을 초과했다.
- 수정한 최초 조회는 딤럼프 1,304ms였다. 장비 목록 쿼리 자체는 딤럼프 120ms, 하이희야 91ms였다. 별도 읽기 전용 Workers 진단 경로에서 운영 Hyperdrive/DB와 실제 핸들러를 사용한 표본이며, 브라우저 전체 로딩 시간이나 모든 계정의 보장 수치가 아니다.
- 계정당 수백만 개의 복사본과 개봉 중 추가 삽입 때문에 전체 수량 조회도 지연될 수 있었다. 4종씩 물리적으로 먼저 제한하는 `MATERIALIZED` 페이지를 사용했다. 첫 수량 페이지 표본은 딤럼프 3,513ms, 하이희야 475ms였다.

## 변경

- 장비창은 `character/loadout?quantities=deferred`로 종류별 대표 인스턴스와 장착 상태를 먼저 받는다. 기존 `(user_id,equipment_id,id)` 인덱스로 종류별 최근 인스턴스를 찾으며, 장착 중인 이전 인스턴스 ID는 유지한다.
- 기존 기본 loadout 응답의 수량 계약은 유지한다. 빠른 응답의 `acquiredAt`은 최신 ID 인스턴스의 획득 시각을 사용한다.
- 정확한 수량은 인증된 `character/equipment/quantities`에서 4종씩 순서대로 조회한다. 미확인 수량은 확인 중으로 표시하며, 실패한 페이지만 재시도한다. 장착·검색·탭 이동은 수량 완료를 기다리지 않는다.
- 수량 응답은 카운터만 갱신한다. 화면을 다시 그리거나 장착 상태를 덮어쓰지 않으며, 이전 조회와 닫힌 화면의 늦은 응답을 무시한다.
- 장비·아바타의 과거 마이그레이션 완료 표시는 묶어서 확인한다. 완료된 스키마 상태만 DB 범위로 캐시하며, 진행 중 DB 작업은 같은 요청 안에서만 공유한다. 스킬칩 중복 조회도 같은 요청 안에서 공유한다.
- 컬렉션 칭호 동기화는 첫 장비 표시 후 시작한다.
- 장비창 전용 384px WebP 47종: 원본 합계 19,588,041B → 1,222,096B. 강화센터 배너: 2,015,969B → 90,342B. 원본은 보존하며 신규 CMS 이미지에는 원본 경로로 대체 표시한다. 재생성: `node scripts/build-equipment-thumbnails.mjs`.
- 설치된 클라이언트의 장비 스크립트도 갱신되도록 리소스 URL과 서비스 워커 정책을 반영했다.

## 검증

- SQLite와 PostgreSQL에서 소유권, 장착 대표 ID, 지급·회수 후 정확한 수량, 페이지 경계, 비공개 항목 필터를 검증했다.
- 수량 지연·실패·재시도, 동시 장착, 탭 유지, 이전 화면 응답 차단 회귀 검사를 추가했다.
- 장비·강화센터·성능 관련 집중 검사 58개와 아바타 검사 85개가 통과했다. 배포 명령은 전체 `release:gate` 통과 후 진행한다.
- 실제 운영 조회를 연결한 별도 QA 화면에서 1440×1000 PC, 390×844 모바일 화면과 검색·장착·칭호/이동수단/스킬칩 탭을 확인했다. 가로 넘침과 깨진 장비 이미지는 없었다. 장착 쓰기는 QA에서만 모의 처리했다.
- PC 진단 추적: LCP 3,118ms, CLS 0. 로컬 QA 프록시를 포함한 값이며 운영 현장 지표가 아니다. 화면 오류는 없었고 QA 서버에 없는 favicon 요청만 실패했다.
- 진단 DB 세션은 읽기 전용이었다. 계정 재화·보유 장비·운영 장착 상태 및 이미지 원본을 수정하지 않았다.

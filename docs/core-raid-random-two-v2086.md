# 붕괴 코어 랜덤 2종 기믹 · 패배 원인 확인

2026-09-12 사용자 승인: 준비된 화면 기믹 3종을 추가하고 한 공략당 랜덤 2종을 배정한다. 같은 작업에서 이유 없는 패배 제보와 오리꿍 계정을 확인한다.

## 배정·판정

- 총 5종: 방향 신호(SEQUENCE), 구속 파쇄(MASH), 코어 동조(CENTER), 회로 복원(CIRCUIT), 차폐 구역(SHELTER).
- 서버의 임의 공략 ID에서 만든 시드로 5종을 섞어 중복 없이 2종을 선택한다. 조합·순서·레이아웃 시드·버전을 `challenge_json`에 저장한다. 재개와 중복 시작은 기존 공략을 반환한다.
- `shared/core-raid-mechanics-v2086.js`가 선택, 레이아웃, 시간 기준과 서버 재판정을 공유한다. 클라이언트의 success/perfect/정답 표시를 신뢰하지 않고 입력 시각·단자·구역을 검증한다.
- 코어 동조는 11초, 정지 3회 중 2회 성공. 다음 회차는 정지 시각 +520ms이며 프레임 지연에 따라 기준 시각을 바꾸지 않는다. 회로 복원은 14초 안에 3쌍. 차폐는 3초 예고와 0.5초 전환을 세 번 반복하며 세 번 모두 회피해야 한다.
- 선택된 2종만 성공/실패와 기존 억제 점수(성공당 50, PERFECT당 10)에 반영한다. 회로·차폐에는 별도 PERFECT 보너스를 만들지 않는다. 기본 피해·보상·입장권·전투력·접근 플래그는 변경하지 않는다.
- 버전 없는 기존 PENDING 공략은 기존 방향+연타를 유지한다. 신형 기믹을 지원하지 않는 이전 클라이언트는 새 공략 생성 전에 426 안내를 받는다.

## 입력 중단 보호

기존 V3 브리지는 QTE 모듈 누락·예외·취소를 실패 결과로 바꾸었고, Core UI는 불완전한 기록도 resolve로 전송했다. 이 경로에서는 기술적 중단이 공대 피해로 이어질 수 있었다.

- 화면 이탈·취소·모듈 오류는 재생을 중단한다. 두 기믹 완료 여부를 브리지와 Core UI 모두 확인한다.
- 서버도 누락·취소·비정상 기록에 422를 반환하고 공략을 PENDING으로 유지한다. 공대 HP와 참가자의 성공/실패 횟수는 변경하지 않는다. 정상적인 시간 초과와 실제 오입력 실패는 기존 규칙대로 처리한다.
- 스킬칩 타임라인의 연출 타임아웃에도 QTE 시간을 포함하며, 복구 과정에서 기믹을 건너뛴 뒤 결과를 제출할 수 없다.
- 최종 결과에는 실제 전투 패배, 선택된 기믹의 결과, 코어 과부하를 구분한다. 과부하는 계산된 편차/허용 편차와 권장 코어를 표시한다. V3 결과 표시는 서버 resolve의 확정 승패를 받는다.

## 오리꿍 읽기 전용 확인

운영 DB에서 닉네임을 정확히 일치시켜 최근 40건 한도의 공략 조회를 수행했고 총 20건이 반환됐다. 기간은 **2026-09-10 20:47:16~20:57:55 KST**다. 완료 19건은 모두 전투와 기존 두 기믹 성공이었다. 이 중 8건은 공략 성공, **11건은 `CORE_OVERLOAD`로 HP 100 감소**였다. 나머지 1건은 미완료였으며 소속 공대는 `PARTY_WIPE`로 종료됐다.

예: 파쇄 248 / 차단 134 / 안정화 240에서 파쇄 +24를 시도하면 편차가 138이 되어 허용 123을 초과한다. 전투·입력 성공과 별도로 과부하 실패가 발생하며 다음 권장 코어는 차단이다. 해당 제보의 기록상 원인은 과부하이고, 모듈 오류로 인한 실패라고 단정하지 않는다. 계정 기록·보상·HP를 수정하지 않았다. 읽기 전용 감사 파일은 배포 디렉터리 밖 `../ops-v2086/orikkung-report.json`에 보존하며 임시 접속 키와 서버는 폐기했다.

## 구현·검수

- HUD: `js/core-raid-screen-qte-v2086.js`, `css/core-raid-screen-qte-v2086.css`. 기존 승인 DOM/SVG 구성을 재사용하고 `.cqm-*`로 범위를 제한한다. 모바일 즉시 입력·드래그·두 번 터치와 보조 기술 클릭이 같은 기록을 남긴다.
- 공통 V3: `js/battle-v3-live.js` 3.32.0, QTE 어댑터 1.2.0. PixiJS 8.20.0 / GSAP 3.13.0, 기존 렌더러·진형·5장 도크·등급 프레임·4개 아트 어댑터를 유지한다. 카드 원화와 SD를 바꾸지 않았다. 새 전투 음원/스프라이트 제작은 없다.
- `npm run test:core-raid`: 46개 검사. 20가지 순서 조합, 서버 추적 재판정, 위조/누락/취소/시간 초과, 기존 PENDING 호환, 재개·중복 반영 방지, 과부하 사례 재현, 일반·스킬칩 V3 재생 중단을 포함한다.
- `scripts/qa-core-mechanics-browser.mjs`: 46개 입력/화면 검사. 360×740, 390×844, 844×390, 1440×1000의 조작부와 원화 유지 확인.
- `scripts/qa-core-random-two-v2086.mjs`: 운영 CSS 57개와 실제 Core UI/V3/QTE를 사용한 오프라인 API fixture의 24개 검사. 모바일 입력 기록을 서버 검증 함수로 전달하고 두 기믹 연속 실행, 취소/로딩 오류의 resolve 무호출, 과부하와 전투 패배 안내를 검사한다. 실제 계정 API는 호출하지 않는다. 공통 V3 회귀 검사 15개도 통과했다.
- Chrome 터치 에뮬레이션 검수이며 실물 iOS/Android 기기 검증을 의미하지 않는다. 전체 배포 게이트와 운영 자산 확인은 배포 기록에 남긴다.

## 배포·복구

메인 앱/SW `2086-core-random-two`, QTE/Core UI `2086-random-two`로 캐시를 갱신한다. `npm run deploy:production` 내부 `release:gate`를 통과해야 배포한다. 새 DB 스키마나 마이그레이션은 없다.

구버전 서버로 단순 롤백하면 2086 PENDING 공략의 새 기믹 기록을 읽지 못한다. 따라서 복구 배포에서도 이번 저장 형식·검증·중단 보호는 보존하고, 필요하면 **신규 배정만 기존 두 종류로 제한**한다. 진행 중 공략은 저장된 2종으로 끝내야 한다. 공략·계정 기록을 삭제하거나 재배정하지 않는다.

# 용병 포지션·CMS 출시 준비안

- 작성: 2026-09-10 · 상태: **배정 초안 / 사용자 검토 대기**
- 검수 화면: `preview/project-v-mercenary-system-v1/positions.html`
- 배정 데이터: 같은 폴더의 `position-draft-v1.json`
- 공통 검증 계약: `shared/mercenary-position-config-v1.mjs`
- 원화·SD·이름·등급의 기준은 계속 `mercenary-system-roster-v1.json` v11이다. 배정 데이터는 코드별 전투 기획 초안이며 별도 캐릭터 로스터가 아니다.

## 1. 이번에 준비한 것

43종의 위치·역할·스킬 표적·고유 임무·약점·배정 근거를 모두 작성했다. 검수 화면에서 개별 편집, 분포 확인, 브라우저 초안 저장, JSON 가져오기·내보내기를 사용할 수 있다. 입력 검증은 화면과 향후 서버가 공유할 수 있는 순수 모듈로 분리했다.

이번 코드는 **기획 초안 편집기**다. 운영 CMS 메뉴·인증·DB 저장·전투 계산·스킬 연출은 연결하지 않았다. 2026-09-11 후속 지시로 C·B·A·S·SS·SSS 등급 초안을 추가했다. 오메가-X는 SSS로 확정하고 나머지 42종은 `null`이다. 전용 스킬과 저장본 변환 기준은 `docs/project-v-mercenary-omega-ranks-v1.md`를 따른다. 화면을 공개해 검토하는 것과 용병 시스템을 출시하는 것은 별개다.

## 2. 실제 코드에서 확인한 문제

| 현재 상태 | 출시 때 필요한 변화 |
|---|---|
| 도감 `positionOf()`가 `role` 문자열 첫 단어를 분리 | 위치·역할을 명시적 필드로 관리. 문자열 분할을 전투 규칙으로 사용하지 않음 |
| `functions/_battle_v2_preview.js`의 `buildFighter()`는 배열의 앞 2명을 FRONT, 나머지를 BACK으로 지정 | 용병은 일반 카드 인덱스와 분리된 `actorKind=MERCENARY`, 고유 ID와 명시적 row 사용 |
| `targetPool()`은 생존 FRONT 우선, 일부 기존 SPEED PVP는 HP형 추격 | 신규 용병 역할을 기존 ATTACK/DEFENSE/HP/SPEED 타입에 강제 치환하지 않음. 용병 표적 규칙을 별도 분기 |
| V3 `ISO_FORMATIONS`는 아군 5곳·적군 5곳이고 `layoutCharacterGrid()`가 인덱스로 접근 | 여섯 번째 원소를 단순 push하면 미정의 좌표에 접근. 별도 용병 앵커 해석과 카드 도크 확장 검수 필요 |
| 배틀슈트는 별도 support, 표적 불가, 독립 시간축 | 용병을 배틀슈트로 위장하지 않음. 용병은 일반 전투 유닛으로 피격·사망·행동 게이지에 참여하는 설계 |
| 운영 관리자는 `requirePermission()`과 별도 제한 ADMIN 경로 검사를 통과 | 신규 CMS도 서버에서 권한 검증. 예측 전용 ADMIN의 권한은 확장하지 않음 |

근거 파일: `preview/mercenary-codex-v1/model.js`, `functions/_battle_v2_preview.js`, `preview/project-v-v3/source/battle/BattleEngine.js`, `functions/api/[[path]].js`. 코드 위치는 후속 구현 시 다시 확인한다.

## 3. 포지션은 세 축으로 나눈다

| 축 | 값 | 의미 |
|---|---|---|
| 배치 위치 `position` | FRONT 전열 / MIDDLE 중열 / REAR 후열 | 시작 위치와 노출 구역 |
| 전투 역할 `role` | 수호 / 돌격 / 기습 / 사격 / 저격 / 제압 / 지원 | 한 슬롯으로 덱의 어떤 약점을 보완하는가 |
| 표적 `basicTarget`, `skillTarget` | 고정 평타 규칙 + 역할별 스킬 표적 | 실제 개입 대상. 사거리·총 종류·의상과 독립 |

- 일반 카드 덱은 정확히 5장, 용병은 별도 선택 슬롯 1개다. 서버 저장 계약은 `cardIds`와 `mercenaryCode`를 유지한다. 위치는 용병 설정에서 서버가 읽으며 유저가 임의 위치·역할을 요청에 넣어 확정하지 못한다.
- 초기 출시는 용병별 고정 시작 위치를 권장한다. 전투 중 자유 배치·임의 이동 명령은 범위에 포함하지 않는다. 역할을 바꾸려면 다른 용병을 선택하게 한다.
- 전열은 서버 `row=FRONT`, 중열·후열은 `row=BACK`을 제안한다. **중열은 신규 피격 우선순위가 아니다.** 실제 3단 피격 판정을 만들려면 기존 엔진 전반을 추가 설계해야 한다.
- 전열 용병은 기존 두 일반 전열에 더해 전선을 유지한다. 마지막 생존 전열이 쓰러질 때만 전열 붕괴로 처리하는 방향이다. 중·후열 용병은 전열이 살아 있을 때 기본 공격의 직접 표적이 되지 않는다.
- 6번은 편성 계약의 논리 슬롯 번호이며 그리드 좌표가 아니다. 일반 카드 5곳을 움직이지 않고, 전술 위치별 용병 전용 앵커를 공용 V3 렌더러에 추가한다. 배틀슈트 `(2,5)` 및 호송 `(1,5)`, 적 진형·목표물과의 충돌을 검사한 후 좌표를 확정한다. 이 초안에서는 좌표를 임의 확정하지 않는다.
- PVP 양 진영의 용병, PVE 용병+배틀슈트 동시 출전, 호송 목표물까지 검사해야 한다. `5+1`은 카드와 용병의 편성 규칙이며 기존 배틀슈트 지원 유닛까지 포함한 렌더 객체 수 제한이 아니다.
- 일반 덱 시너지·기존 일반 카드 타입 개수에는 용병을 자동 합산하지 않는다. 회복·보호 효과는 일반 카드와 용병을 포함한 총효율 관점에서 별도로 검수한다.

## 4. 7가지 역할과 선택 이유

| 역할 | 수 | 위치 | 가져오는 이점 | 반드시 남길 약점 |
|---|---:|---|---|---|
| 수호 | 4 | 전열 | 핵심 카드 보호·전선 유지 | 낮은 처치력, 관통·장기 소모 대응 한계 |
| 돌격 | 10 | 전열 | 적 방어선 압박·근접 돌파 | 접근·공격 동작 의존, 집중 공격에 취약 |
| 기습 | 5 | 전열·중열 | 약화된 적 처치, 스킬로 후열 개입 | 낮은 생존력, 보호·타이밍 실패에 취약 |
| 사격 | 11 | 중열·후열 | 안정적 지속 화력 | 즉시 처치·광역 제압을 동시에 갖지 않음 |
| 저격 | 4 | 후열 | 준비 후 정밀 단일 타격 | 긴 준비, 접근·보호막 대응 한계 |
| 제압 | 6 | 전열·중열·후열 | 약화·행동 방해로 공격 기회 생성 | 제어 저항, 개인 처치력 제한 |
| 지원 | 3 | 전열·중열·후열 | 지휘·보호·회복 중 하나에 집중 | 낮은 직접 피해, 지원을 받는 팀 의존 |

덱이 먼저 무너지면 수호, 버티지만 못 뚫으면 돌격, 적 핵심이 살아남으면 기습·저격, 안정적인 피해가 부족하면 사격, 공격 기회가 부족하면 제압, 기존 카드 성능을 살려야 하면 지원을 고른다. 모든 역할이 특정 콘텐츠의 필수 입장 조건이 되는 설계는 피한다.

사격+돌격 21명, 지원 3명인 분포를 균등한 숫자로 억지 보정하지 않는다. 지원은 라비에나의 공격 지휘, 연휘의 전열 보호, 미레시아의 회복으로 차별화한다. 특히 회복 선택지가 1명뿐이므로 단일 용병의 필수화·희귀도 종속을 출시 검수 항목으로 둔다. 현재 등급·출현 확률은 정하지 않는다.

## 5. 표적·스킬 설계 규칙

1. 용병 기본 공격은 `FRONT_ENEMY`로 통일한다. 생존·표적 가능 대상만 후보이며 배틀슈트, 호송 목표물, 소환 장식은 제외한다. 전열이 없으면 생존 적 전체로 전환한다.
2. 기습과 일부 저격은 **스킬에만** 후열·약화 표적 규칙을 쓴다. 기존 일반 SPEED 카드의 PVP HP형 우선 로직을 무조건 복사하지 않는다.
3. `BACK_THREAT`는 생존 후열 중 전투 시작 때 확정된 공격력이 가장 높은 대상이다. 후열이 없으면 전열 우선. 실시간 버프 변경으로 조준 표적이 매 프레임 바뀌지 않게 한다.
4. `LOW_HP_ENEMY`와 `ALLY_LOW_HP`는 현재 HP / 최대 HP 비율을 비교한다. 동률은 슬롯 순, 이어 서버 고유 ID 순으로 고정한다. 선택 시점과 타격 시점 사이의 사망은 서버가 재선정하며, 클라이언트에서 임의 피해를 옮기지 않는다.
5. 보호 스킬은 보호 대상이 명시된 경우에만 재지정·가로채기를 수행한다. 모든 수호형이 모든 기습을 상시 차단하지 않는다. 도발·가로채기 우선순위는 개별 스킬 명세 확정 후 명시하고 회귀 검사한다.
6. `FRONT_GROUP`은 적 전열 집단, 전열이 없으면 단일 대상이다. 최대 대상 수·총 피해 예산·분산 방식은 후속 수치 검수에서 확정한다. 표적 수가 늘어 피해가 무제한 증폭되는 곱연산은 피한다.
7. 제압은 첫 출시부터 기절·침묵·행동 지연을 전부 부여하지 않는다. 용병별 주 제어 1개를 먼저 선택하고 지속시간·재적용 제한을 설정한다. 보스 저항 시 대체 약화 효과가 필요한지 모드별 검수한다. **현재 JSON에는 미구현 효과 ID나 수치를 넣지 않는다.**
8. 지원 전체 대상은 생존 일반 5장+용병이다. 회복·보호막·부활은 서로 다른 효과이며, 제안 설명에 없는 부활을 임의 추가하지 않는다. 기존 회복 총량·연장전·회복 중복 제한과 상호작용을 검수한다.
9. 동일 역할 안에서도 임무, 표적, 준비/지속 흐름, 약점 중 최소 두 항목을 구분한다. 신규 용병에 상위 등급이라는 이유로 하위 역할의 장점을 전부 합치지 않는다.

현재 표적 enum은 검증된 **설정 선택지**이며 서버 표적 선택 함수는 아직 구현하지 않았다. 일반 타입의 피해 공식·필살기·시너지와 혼합 적용하기 전 효과별 계산 순서를 확정해야 한다.

| V-043 | 동탄 디임 | 중열 | 사격 | 권총 지속 속사 |

주요 재분류: 서윤은 기존 후열에서 중열로 제안한다. `마법`, `격투`, `지원사격`은 무기·연출 설명이므로 솔레아·세실리아·기관총 용병은 실제 임무인 제압으로 분류했다. 연휘는 수호 탱커와 구분되는 전열 보호 지원이다.

## 7. CMS 설정 계약

### 준비된 초안 스키마

| 필드 | 편집 | 검증 |
|---|---|---|
| `format`, `schemaVersion` | 고정 | 알려진 형식·버전만 허용 |
| `revision` | 로컬 저장 시 증가 | 안전한 정수, 저장본 수정 번호와 일치 |
| `rosterVersion` | 고정 | 원화 기준 로스터 버전과 일치 |
| `status`, `runtimeEnabled` | 고정 | `DRAFT`, `false`만 허용 |
| `assignments[].code` | 고정 | 기준 로스터의 모든 코드 정확히 1회 |
| `rank` | 미확정 카드만 가능 | `null` 또는 C/B/A/S/SS/SSS. 오메가 SSS는 고정 |
| `position`, `role` | 가능 | 3개 위치·7개 역할의 허용 조합 |
| `basicTarget` | 고정 | `FRONT_ENEMY` |
| `skillTarget` | 가능 | 역할별 허용 표적 enum |
| `specialty`, `weakness`, `rationale` | 가능 | 각각 공백 제외 내용 필수, 최대 240자 |

기준 로스터 이름·이미지·해시·공식 등급을 가져오기 파일로 덮어쓸 수 없다. 등급 초안은 허용된 6단계만 받는다. 알 수 없는 키, `enabled=true`, 체계 밖 등급·가격·확률, 누락·중복 용병, 잘못된 역할·표적, 잘못된 JSON, 128 KB 초과 파일은 거부한다. 가져오기 실패 시 현재 편집 내용과 저장본을 유지한다.

저장은 `cnine.mercenaryPosition.draft.v1` 브라우저 키만 사용한다. 일반 계정·운영자 토큰·CMS API는 읽지 않는다. 공개 프리뷰의 편집 권한은 서버 관리 권한을 뜻하지 않는다. 다른 탭에서 저장된 수정 번호가 달라지면 덮어쓰지 않고 재로딩을 요구한다. 브라우저 저장소는 DB의 원자적 동시성 제어를 대체하지 않는다.

### 실제 CMS에 추가할 화면

| 구역 | 항목 | 현재 준비 상태 |
|---|---|---|
| 기본 정보 | 코드, 이름, 원화·SD, 승인 이력 | 기존 로스터 조회 |
| 포지션 | 위치, 역할, 평타·스킬 표적, 임무·약점 | 편집·검증·JSON 준비 완료 |
| 등급·성장 | 사용자 확정 등급, 성장 한도, 스탯 기준 | 등급 6단계 초안 편집 가능, 오메가 SSS 확정. 성장·스탯 미정 |
| 스킬 | 승인된 효과 ID, 계수, 준비·재사용, 대상 수, 상태이상 제한 | 방향만 작성. 실행 코드·임의 효과 문자열 입력 금지 |

### 후속 서버 구현 계약 — 아직 등록된 라우트가 아님

- `GET /api/admin/mercenaries/settings`: 저장된 draft/published revision, 원화 로스터 버전, 변경점 반환.
- `PUT /api/admin/mercenaries/settings/draft`: `{expectedRevision, reason, draft}`. 공유 검증 후 서버 권한 확인, 수정 번호 조건부 UPDATE. 충돌은 HTTP 409, 미지원 값은 400. 빈 사유 거부.
- `POST /api/admin/mercenaries/settings/publish`: OWNER 최종 적용. 프런트 요청의 승인 boolean을 믿지 않고 서버의 등급 확정·스킬 검수·출시 승인 기록을 조회. 미충족 시 409.
- 초안 저장 권한은 새 `MERCENARY_MANAGE` 권한을 제안하며 기존 `requirePermission()`을 사용한다. 현재 예측 전용 ADMIN의 경로 제한은 유지한다. UI 숨김만으로 권한을 구현하지 않는다.
- 설정 저장과 `admin_logs`의 before/after·운영자·사유·revision을 같은 원자적 작업으로 처리한다. 게시 revision은 불변 스냅샷으로 남기고, 복원은 이전 스냅샷으로 새 revision을 생성한다.
- 전투 시작 때 게시 설정 revision과 용병 파라미터를 스냅샷에 고정한다. 진행 중 전투·PVP 방어 편성의 설정 변경 적용 시점을 명시하고, 리플레이는 해당 revision을 재사용한다.
- 저장소를 `app_meta`로 시작할지 전용 테이블로 분리할지는 DB 구현 시 선택한다. D1/운영 Postgres 호환 계층에서 조건부 갱신·로그 원자성을 모두 검증한다. 이번 작업은 마이그레이션을 실행하지 않는다.

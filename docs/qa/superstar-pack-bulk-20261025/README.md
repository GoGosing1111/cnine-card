# 슈퍼스타팩 1,000회·10,000회 빠른 개봉

2026-10-25. 구현·검증 완료, 운영 배포 준비 중.

## 범위와 규칙

사용자 `슈퍼스타팩도 1000장 10000장 개봉 추가해 똑같이 빠르게`에 따른다. 기존 1회·10회는 유지하고 1,000회·10,000회 전용 버튼을 추가한다. 현재 운영 단가 3억 코인으로 각각 3,000억·3조 코인이다. 매회 독립 당첨 10%·꽝 90%, 당첨 보장 없음, 기존 공개 SUPERSTAR 7종 균등 선택, 중복 조각 600개를 유지한다. 운영 설정·계정에 검증용 쓰기를 하지 않았다.

기존 얼티메이트 일괄 결과 UI와 승인 공통 패널/버튼을 재사용한다. 별도 원화나 의존성 복사본을 만들지 않는다. 1회·10회 스와이프는 기존대로, 빠른 개봉은 한 번의 결제 확인 후 영상 대기 없이 당첨·꽝 합계와 종류별 이미지/수량을 보여준다. 상세보기는 필요할 때 50종, 이미지는 최대 24종씩 렌더링한다.

## 서버·복구

- 기존 `superstar-pack/draw`와 영수증/차감 테이블을 확장한다. `SUPERSTAR_BULK_V1` 영수증은 합계와 당첨 종류별 수량만 저장하며 요청은 `ssb-<시각>-<UUID>`와 확인한 총액을 요구한다. 1회·10회 경로로 일괄 요청을 재사용할 수 없다.
- 기존 난수 판정 함수를 사용한다. 암호학적 난수를 4,096개씩 받아 호출 비용을 줄이며 매회 당첨·카드 선택 두 값을 그대로 사용한다. 꽝을 당첨으로 보장하거나 묶음 확률로 바꾸지 않는다.
- 카드 지급은 종류별로 묶고 모든 개별 당첨 로그는 30행씩 INSERT한다. 10,000회 모두 당첨되는 조건도 낱장마다 카드 UPDATE/별도 요청을 만들지 않는다.
- 기존 PENDING 계정 유일 인덱스·차감 유일 키·지갑 행 잠금·지급 전후 검증으로 결제·카드·조각·로그·영수증을 함께 확정한다. 일괄 거래는 결제 직전 CMS 설정 원문도 대조한다. 확률/가격/OFF 변경이나 실제 지급 누락은 전체 거래를 취소한다.
- 로컬 영수증은 실제 `serverUserId`별로 보관한다. 같은 요청 복구로 추가 차감을 막고, 영수증이 없는 24시간 초과 요청은 차단한다. 이미 완료된 오래된 영수증은 판매 OFF에도 복구된다. 처음 응답과 복구 응답 모두 최신 잔액/보유 수량을 읽는다.
- 기존 다중 탭 개봉 잠금을 사용하며, 일반/얼티메이트/슈퍼스타의 미확인 거래를 먼저 복구한다. 계정 변경에는 결과 적용을 중단하고 원래 계정의 요청을 보존한다.

## 검증

- 관련 자동 검사 80개 통과. 신규 일괄 검사 20개와 기존 슈퍼스타·얼티메이트 60개다. 실제 PostgreSQL(PGlite)과 운영 호환 계층으로 1,000/10,000회 전부 꽝·현재 확률·전부 당첨, BIGINT 3조 결제, 중복 600조각, 각 당첨 로그, 동시 요청, 가격/지갑/보유 변경, 지급/로그/영수증 억제 트리거, 응답 유실, 만료·잘못된 요청을 검증했다.
- 실제 앱 진입 함수·상점 버튼·잠금·공유 결과 모듈을 PC 1440, 모바일 390(CPU 4배 제한), 320에서 검증했다. 각각 두 수량 POST 1회, 현재 7종 이미지, 상세를 열기 전 DOM 행 0, 가로 넘침·페이지 오류 0. 응답 유실 후 재접속과 같은 요청 재조회 추가 결제 0, 계정 변경 후 원래 영수증 보존을 확인했다. 기존 얼티메이트 10만 장 브라우저 회귀도 통과했다.
- 실제 API Runtime Worker 엔트리를 메모리에서 번들 컴파일했다. 임시 빌드 파일은 만들지 않았다.

## 서버 성능

운영 설정·후보 7종을 READ ONLY로 읽고 실제 슈퍼스타 핸들러, 암호학적 RNG, 운영 PostgreSQL 어댑터를 Cloudflare 임시 프리뷰(HKG) → Hyperdrive → Neon에서 실행했다. 11개 테이블과 뷰를 임시 스키마에 먼저 만들고 DB의 READ ONLY를 켠 뒤 실제 지급 경로를 실행했다. 영구 테이블 DML은 DB가 차단하며 각 실행 종료 ROLLBACK 후 임시 관계 0개를 확인했다.

| 조건 | 횟수 | 평균 | 최소~최대 |
|---|---:|---:|---:|
| 현재 확률 1,000회 | 5 | 364.6ms | 339~463ms |
| 현재 확률 10,000회 | 5 | 460.4ms | 403~634ms |
| 임시 100% 당첨 10,000회 | 5 | 661.2ms | 563~963ms |
| 임시 전부 꽝 10,000회 | 5 | 313.2ms | 292~393ms |

현재 확률의 응답은 약 3KB·7종이다. 100%/0%는 임시 최악 조건이며 운영 설정에 저장하지 않았다. 인증·실제 사용자 락 경쟁·운영 테이블 규모·클라이언트 통신·실제 COMMIT 영속화는 포함하지 않으므로 고객 전체 개봉시간 보장이 아니다. 외부 READ ONLY 거래를 유지하기 위해 내부 BEGIN/COMMIT만 SAVEPOINT/RELEASE로 바꿨다. 브라우저 시간은 별도의 로컬 임시 DB 측정이다.

# 이스겐 공격 요청의 계정 잠금 충돌 보정

새 제보: https://www.playdk.kr/board/skm/1538912 (열람 당시 댓글 0개). 이용자는 공격을 4회 눌렀으나 ‘같은 계정’ 안내가 떴다고 설명했다. 이 문구는 계정 전체 요청 잠금의 거절 응답과 일치한다. 기존 전투 영수증은 성공한 요청만 저장하므로 이를 실제 클릭 횟수나 미참여의 근거로 삼지 않는다.

찬호가 포함된 운영 실패 회차는 최종 HP 114,284에서 마지막 성공 공격 이후 6.8초가 남아 있었다. 같은 세 명의 직전 회차는 정상 CLEAR였다. 운영 기록은 READ ONLY로 확인했다. 과거 거절 요청 자체와 당시 잠금 소유 작업은 남아 있지 않아 특정 작업이 잠금을 남겼다고 단정하지 않는다. 원본 계정/덱 스냅샷은 프로젝트 루트 operations/isgen-final-window-20261117에만 보관한다.

## 원인과 수정

`raid/lich/action`은 공대 행의 CAS, 개인 행동 토큰, 계정별 요청 영수증, 피해·보상 원자 거래를 갖추고 있는데 그 앞에서 계정 전체 잠금도 획득했다. 20초 잠금이 남거나 다른 작업이 처리 중이면 12초 최종 공격 시간 동안 유효한 입력이 거절될 수 있었다. 기존 제한 재시도만으로는 이를 해소할 수 없다.

이스겐 전투 입력만 기존 공대 거래로 직접 처리한다. 방 생성/참가/편성/출정/퇴장은 계정 잠금을 유지한다. 인증, 콘텐츠 접근, 참가자·퇴장 여부, 토큰, 개인 쿨다운, 마감, 영수증, 공대 CAS와 보상 한도는 그대로다. 다른 요청의 잠금을 해제하거나 빼앗지 않는다. 상태 조회가 전투를 진행·정산할 때도 이미 같은 공대 CAS를 사용한다.

피해량·인원 배율·보스 HP·제한시간과 기존 클리어/실패 결과는 변경하지 않는다. 서버 코드 한 곳의 분기 수정이며 클라이언트 자산·캐시 버전 변경은 필요하지 않다.

## 검증

수정 전 실제 UserMutationLock 구현에 20초 잠금을 유지하면 유효한 공격은 동일 문구의 409로 거절됐다. 수정 후 같은 조건의 네 번 입력은 685,728 → 400,006 → 114,284 → 0으로 반영되고 한 번 클리어됐다. 타 작업 잠금은 계속 유지됐다.

SQLite/PostgreSQL 호환 경로에서 동일 토큰 동시 입력의 피해 1회, 같은 영수증 재시도, 동시 막타, 정산 실패 전체 롤백, 비참가자 차단을 검사한다. 기존 개인 기믹·3~6인 클리어·기존 계정 충돌 재시도·상태 응답 역순·주간 보상 한도 검사도 배포 범위에 포함한다.

PC/Android/WebKit/Windows 진입 URL/H5 iframe의 실제 로비 메뉴에서 첫 진입·재진입·공격 4회·결과·퇴장을 수정 전후 비교했다. 운영 계정으로 시험 공격·지급은 하지 않았다. 에뮬레이션과 측정 한계, 기존 WebKit 경고와 긴 프레임은 performance.json에 기록한다. 종료 후 전장 요청은 0건이다.

배포 확정값과 최종 검사 결과는 completion.json에 기록한다. 공개 공지 초안은 공지문.txt이며 게시글/댓글/메시지는 발송하지 않는다.

# 무한의탑 120층 · 성장 난도와 완료 정산

사용자 요청: “스킵제한 두고 성장한계에 맞춰 새난이도 설정해 보상도 10배 ~20배 올려도 됨”. 후속 선택은 “101~120층 추가, 기존 진행도 유지”다.

## 적용 정책

기존 시즌을 120층으로 확장한다. 기존 최고층·현재 도전층·수령 이력을 유지하며, 100층 완료자는 101층부터 진행한다. 이미 완료한 층의 재등반이나 상향분 소급 지급은 없다. 전투 시작 시 확정한 난도·편성·코인 보상은 재접속이나 CMS 변경으로 재추첨하지 않는다.

| 구간 | 최초 클리어 코인 |
|---|---:|
| 1~50층 | 기존 CMS의 10배 |
| 51~80층 | 기존 CMS의 15배 |
| 81~100층 | 기존 CMS의 20배 |
| 101~109층 | 각 500억 |
| 110층 | 6,000억 |
| 111~119층 | 각 600억 |
| 120층 | 8,000억 |

70/80/90/100/110/120층 수호자 전투력은 각각 3,000만/6,000만/1억6,000만/4억/9억/18억이다. 사이 층은 로그 보간으로 단조 증가한다. 보상 배수는 코인에 적용하며 아이템 확률·계급 EXP는 기존 정책이다. 도감 수집 보너스 전 총 기본 코인은 1~100층 1조 8,152억 5,000만, 신규 20층 2조 3,900억이다. 전체 120층 상세는 `floor-plan.json`이다.

## 완료와 복구

- `tower/start`: 실제 서버 저장 덱으로 전투를 계산하고 압축된 고정 기록과 계정의 미완료 전투 포인터를 저장한다. 보상·계급 EXP·층 상승은 없다.
- `tower/finish`: 전투 공식 경과 시간과 행동 수로 정한 서버 최소 완료 시간(8~180초)을 충족해야 정산한다. 클라이언트는 기존 전체 재생·일시정지를 유지하고 조기 결과 버튼을 제공하지 않는다. 서버 시계는 속도 우회 억제 기준이며 브라우저 프레임 시청 인증은 아니다.
- 코인·코인 로그·계급 EXP·층 진행도·강화 보호권·고급 재설정권·전투 이력·핵심 정산 영수증은 같은 거래다. 추가 마법/장비/블랙미라클 보상은 기존 고정 영수증으로 복구하며 성공한 단계는 다시 실행하지 않는다.
- 시작/정산 응답 유실, 다른 기기의 재진입, 추가 지급 오류는 같은 전투로 복구한다. 진행도나 시즌을 운영자가 변경하면 미정산 전투를 취소하고 활성 포인터를 해제한다. 구버전 `tower/fight` 즉시 지급은 새로고침 안내로 차단한다.
- 기존 인증·계정 잠금·공통 거래 기반을 그대로 사용하며 신규 DB 스키마는 없다. 전투 재생 시간 동안 DB 잠금을 잡거나 서버에 주기적으로 진행률을 전송하지 않는다. 대기 시간은 브라우저 타이머로 표시하고 이른 완료 요청만 한 번 더 보낸다. 전투 본문은 gzip으로 저장하며 원문은 4 MB 이내로 제한한다.

## 난도 측정

최근 7일 활동 일반 계정 중 저장 PVE 덱이 있는 230개 계정을 모집단으로 삼았다. 진행 구간에 고르게 뽑은 계정과 100층 완료자·Lv.10 이상 용병 보유자를 합친 57개 실제 저장 덱을 읽기 전용으로 캡처했다. 원본 계정 식별자와 덱은 저장소 밖에 보관하고 이 폴더에는 집계만 저장했다.

`measurement.json`: 실제 서버 전투 엔진, 11개 층, 고정 시드 8개와 성장 가정을 포함한 5,816회. 100층 완료자 10명의 현 편성은 100층 승리 90%, 110층 10%, 120층 0%였다. 같은 편성에서 용병만 +2레벨/필요 돌파를 적용하면 110층은 32.5%였다. `growth-ceiling.json`의 960회 추가 비교에서는 용병 Lv.20/돌파 완료 가정으로 120층 전투력 18억에서 90%였다. 현재보다 성장할 이유가 있고 최종 성장으로 도달 가능한 구간을 목표로 선택했다. 표본의 구성·계정별 카드와 장비 차이가 있으므로 실전 승률 또는 모든 용병의 동일 성능을 보장하지 않는다.

평균 계산 시간은 로컬 표본 기준이며 운영 지연 시간 추정으로 쓰지 않는다. 큰 전투 응답도 약 1.36 MB로 저장 제한 안에 있었다. 다른 콘텐츠 전투 공식이나 용병 성장 수치는 변경하지 않았다.

## 검증과 배포 범위

관련 서버 검사는 SQLite와 PostgreSQL에서 조기 정산 차단·계정 분리·중복 지급·실패 롤백·응답 유실·추가 지급 복구·운영 진행도 변경을 검사한다. 일회 CMS 도구 검사는 변경 충돌·dry-run·감사 기록 실패 롤백·재실행·기존 100층 완료자 보존과 전체 120층 설정 해시를 검사한다.

PC 1440px, 모바일 390px에서 실제 배포용 컨트롤러/전투 번들과 격리 DB의 실제 API 경로를 연결한다. 전투 중 보상 0, 조기 결과 없음, 모바일 일시정지·재입장·완료 응답 유실 후 동일 영수증 복구, 코인 1회 지급과 다음 층 표시를 확인한다. 음소거 후 검사하며 운영 계정을 사용하지 않는다. 기존 탑 전용 ImageGen 프레임·봉인·버튼·배경을 사용한다. 화면 기술 검수는 사용자 시각 승인이 아니다.

이번 변경은 무한의탑 안의 전투 수명주기·설정·표시에 한정한다. 공통 인증/DB/거래 기반·스키마·런타임 의존성 변경은 없다. 따라서 `deploy:production -- --scoped`로 탑 거래/정책/화면/입장 연결/장비 보호권 연결/전달 자산 검사와 Worker 구문 검사를 선택한다. 작업 시작 당시 운영 소스는 `ab12ecbd67000be091802d59122c710c004763fa`였다. 배포 직전 봉인구 전용 원화 변경이 먼저 배포되어 최신 원격을 통합했다. 실제 최종 기준은 `fd7907c0c13394e82d8db307ebb3ba958ab5ee13`(Pages `f7c30702-0cab-4cba-845f-499c8e679e00`)이다. 원격의 봉인구 전용 변경과 정책은 보존했으며 탑 코드에는 충돌이 없었다. 현재 공용 로더 연결 검사도 배포 검사에 포함한다.

운영 설정은 배포된 프로토콜을 확인한 뒤 `ops:tower-abyss-growth:20261022:v1` 한 번만 적용한다. 적용 직전 CMS 해시가 달라지면 중지하고, 전체 설정·감사 로그·영수증을 단일 거래로 저장한다. 이후 운영자의 CMS 편집은 재배포/재실행으로 덮어쓰지 않는다. 실제 반영 증빙은 후속 `live-verification.json`에 기록한다.

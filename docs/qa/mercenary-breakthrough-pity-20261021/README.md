# 용병 돌파 실패 천장과 과거 기록 반영

사용자 요청: “용병 돌파 천장 만들어 10회로 이전꺼까지 계산해서 소급적용 20레벨은 20회”. 후속 답변으로 **“10회·20회 실패 후 다음 시도 확정”**을 확정했다.

- Lv.5·10·15: 같은 용병, 같은 단계에서 10회 실패한 뒤 다음 돌파 확정 성공.
- Lv.20: 20회 실패한 뒤 다음 돌파 확정 성공.
- 일반·리미티드에 동일한 천장. 기본 성공률 10%, 기존 경험치 필요량·재료·기본 1장 보호·성장 능력은 유지한다. 천장 도달 후에도 현재 단계 경험치 100%가 필요하다.
- 실패하면 현재 경험치만 0. 성공하면 해당 단계 실패 누적이 초기화되고 다음 단계로 넘기지 않는다. 최종 돌파 후에도 Lv.20이다.

## 소급 방식

`joint_operations_v1`의 계정별 `MERCENARY_LEVEL_V1` 완료 영수증을 유일한 실패 원장으로 사용한다. 배포 전의 완료 실패도 조회 즉시 합산한다. 별도 카운터 이관·날짜 경계·계정별 초기화 작업 없이 과거와 새 실패를 같은 기준으로 집계하므로 운영 시도와 소급 작업 사이에서 횟수가 누락되거나 중복되지 않는다.

계정·용병 코드·미완료 돌파 단계와 성장 revision을 대조하고, 성공 이후의 실패만 남긴다. 재료 전수, PENDING/CANCELLED, TEST, 다른 용병·다른 계정·성공한 단계는 포함하지 않는다. 과거 완료 영수증의 결과·재료·XP는 바꾸지 않으며 추가 지급/환급은 없다. 기존 미완료 실패 요청이 이미 새 천장 조건을 충족했다면 소모 없이 취소하고 최신 상태의 확정 돌파로 다시 요청한다.

신규 판정의 실패 횟수·천장·실제 성공률과 결과는 기존 영수증에 함께 고정한다. 계정 잠금, 성장 revision 검사, 동일 거래 완료, 응답 유실·재시도 복구를 유지한다. 클라이언트가 실패 횟수를 보내는 요청은 허용하지 않는다. 스키마·공통 거래 기반·CMS 수치는 변경하지 않는다.

## 화면

기존 성장실과 전용 봉인/버튼 이미지·정보 문단 체계를 유지한다. 실패 누적, 과거 기록 포함, 천장 달성 및 성공 확률 100%를 DOM으로 표시한다. 경험치가 부족한 천장 대상에는 충전 후 확정 돌파 가능 안내를 표시한다. 결과에도 실패 누적 또는 천장 확정 성공을 표시하고 과거 영수증 재생에는 당시 결과만 사용한다. CMS에는 고정 천장 기준과 기본 확률의 의미를 안내한다.

## 검증

- SQLite/PostgreSQL 관련 신규 검사 10개: 10/20회 실패 경계, 과거 37회 실패, 단계 초기화, XP 충전, 동일 UUID 재시도, 동시 요청, 원자 롤백, 다른 계정·용병·TEST 제외, 과거 완료/미완료 영수증 호환.
- HTTP 검수 fixture의 Origin 누락을 수정하고 위조 횟수 차단 2조건을 실제 `JOINT_BODY` 오류로 재확인했다. 이는 검수 요청 수정이며 운영 Origin 검사는 유지한다.
- PC 1440px·모바일 390px에서 실제 서버 핸들러에 연결한 격리 계정으로 누적 표시→확정 돌파→결과→다음 단계 초기화, Lv.20의 19/20회 차이와 최종 완료를 확인한다. 운영 계정은 사용/소모하지 않는다. 작은 능력치와 300 EXP는 격리 fixture 값이다.
- 운영 읽기 전용 대조: 2026-10-21 14:45 KST, 성장 249행/127명과 완료 영수증 2,127건을 독립 집계와 대조해 전부 일치했다. 현재 미완료 단계 실패는 40명·48용병·175회, 천장 도달은 3용병(10/13/37회)이다. 운영 활동에 따라 이 수치는 달라진다.
- 추가 조회는 기존 `(user_id,kind,created_at)` 인덱스를 사용한다. 측정 표본 최대 121행, 현지 DB 왕복 포함 76.87~87ms. 전역 영수증 전수 조회를 HTTP 경로에 추가하지 않았다. 변경 경로의 실제 자료·계획은 `docs/qa/mercenary-breakthrough-pity-20261021/history-before.json`에 기록한다.

국소적인 용병 돌파 판정/표시 변경이므로 관련 성장 회귀와 Worker 컴파일을 선택한 scoped 배포를 사용한다. 완료 배포 식별자와 운영 재조회는 검증 폴더에 이어 기록한다.

첫 배포 게이트에서 V2 성장·영수증 UI 등 16개 검사는 통과했고, 기존 할로윈 검사 2개가 8종을 순회하면서 재료 차감을 7종으로 고정한 비교값 때문에 실패했다(실제 696장/기대 734장). 변경 전 실제 배포 커밋 `267da6bfe`의 서버/성장 모듈을 로더로 대체해도 SQLite에서 동일하게 재현됐다. 해당 카탈로그와 테스트는 이번 변경 전후 동일하다. 무관한 카탈로그/검사를 수정하지 않고, 이미 통과한 V2/UI 검사를 반복하지 않으며 아직 실행하지 않은 돌파 준비/거래 회귀와 Worker 컴파일로 scoped 전달을 마친다. 첫 게이트와 재현 근거는 검증 폴더에 보존한다.

후속 돌파 준비/거래 22개와 Worker 컴파일은 통과했다. 업로드 전 파일 수가 20,001개로 기존 20,000개 상한을 넘겨 전송이 중단됐다. 게임에서 참조하지 않는 본 구현 문서만 기존 업로드 제외 경로인 `docs/qa/mercenary-breakthrough-pity-20261021/README.md`로 옮겨 Git에 보존했다. 이미지·게임 자산·프리뷰·배포 도구와 파일 수 제한은 그대로 유지한다.

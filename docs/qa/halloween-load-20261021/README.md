# 할로윈팩 개봉·이전 결과 확인 빈도 조사 — 2026-10-21

사용자 요청: “할로윈팩 전체적으로 개봉이 많아서 그런지 병목현상 과부화 확인해봐 이전결과확인 빈도가 높아짐”. 조사 시각은 2026-10-21 13:01~13:10 KST다. 이 작업은 진단이며 운영 코드·확률·재화·계정·발행량을 수정하거나 새 개봉을 실행하지 않았다.

## 결론

측정 시점에는 전체 서버/DB 과부하나 할로윈 개봉 처리 적체를 확인하지 못했다. 반면 실제 개봉의 409 응답과 영수증 404 응답이 관측됐고, 이런 일시 거절을 클라이언트가 한 번만 재조회한 뒤 `HALLOWEEN_RECOVERY_REQUIRED`로 바꿔 새 개봉을 잠그는 흐름을 재현했다. 먼저 구분할 대상은 전역 용량 부족보다 **계정 단위 요청 충돌·미접수 요청의 복구 정책**이다.

원격 로그에는 HTTP 상태만 있어 관측된 409의 응답 본문 코드는 확보하지 못했다. 따라서 그 한 건을 `JOINT_LOCK_BUSY`라고 확정하지 않는다. 아래 모의 재현은 해당 코드에서 같은 안내가 발생함을 입증하며, 이용자별 원인과 과거 발생률 증가를 확정하는 자료는 아니다.

- 공개 설정 GET을 별도로 4회 읽었을 때 모두 200, 전체 수신 188~265ms, revision 19, 개봉 가능이었다.
- 개봉 요청에는 여러 DB 읽기·원자 거래가 포함된다. 표본상 정상 개봉은 통상 단독 쿼리 17~20건과 batch 2회였으며 네트워크/처리 비용 개선 여지는 있다. 지금의 정상 응답 시간만으로 이를 과부하 원인이라고 결론 내릴 수는 없다.

## DB와 시간대별 개봉량

- 직접 연결은 세션 전체를 read-only로 설정하고 각 쿼리를 3~5초로 제한했다. 넓은 집계 2개는 5초 제한으로 중지돼, 기존 `(user_id,kind,created_at)` 인덱스를 이용하는 50/200계정 묶음으로 범위를 좁혔다. 제한 해제·새 인덱스·VACUUM·전체 부하 시험은 하지 않았다.
- 현재 계정 3,880개를 두 집단(용병 보유 420·나머지 3,460)으로 확인했다. 07:06:49 KST 이후 약 6시간 구간에서 **완료 70,079건, 취소 1건, PENDING 0건**이었다. 각 묶음은 읽은 시점이 달라 단일 원자 스냅샷은 아니다. DB에 접수되기 전 거절된 요청은 이 집계에 포함되지 않는다.
- 완전한 시간 단위 비교: 08시대 16,274건, 09시대 14,244건, 10시대 9,486건, 11시대 5,381건, 12시대 6,354건. 조사 직전 시간대가 오전보다 개봉 요청량이 증가한 상태는 아니었다. 건수는 1회/10회 묶음을 각각 개봉 요청 한 건으로 센 값이다.
- 점검 중 연결은 67→95/최대 901, 대부분 idle였다. 관측된 잠금 대기 0, 누적 deadlock 356→356으로 증가 없음. 약 6분의 pg_stat_statements 차이에서 주요 영수증/획득 쿼리 평균 실행 시간은 약 0.03~0.60ms였다. 계정 개봉 이력 목록은 약 23.9ms였으며 현재 할로윈 개봉의 필수 경로가 아니다.
- `completed_at`은 batch 전 작성되므로 `completed_at-created_at`을 전체 결제/응답 지연으로 보고하지 않는다. 지연 표는 실제 Worker wall time을 사용한다.

## 클라이언트에서 확인된 취약점

`shared/mercenary-halloween-session-v2.mjs`의 `submit()`은 terminal 목록에 없는 개봉 오류 뒤 영수증 GET을 **한 번** 실행한다. 여기서 완료 영수증을 얻지 못하면 원래 오류 코드를 안내에 보존하지 않고 `HALLOWEEN_RECOVERY_REQUIRED`로 바꾼다. pending을 보존하므로 새 1회/10회와 자동 개봉이 중지된다.

운영과 SHA-256이 일치하는 세션 모듈에 격리 응답을 주입했다. POST `JOINT_LOCK_BUSY` 409 → GET `JOINT_NOT_FOUND` 404이면 POST 1회·GET 1회 후 “이전 결과 확인으로 같은 개봉 요청을 복구해 주세요.”가 표시되고 pending이 남았다. 같은 방식의 `USER_ACTION_IN_PROGRESS`도 같은 결과였다. 실제 계정 개봉 POST는 실행하지 않았다.

서버 `withJointUserMutationLock()`은 같은 계정의 다른 행동이 잠금을 보유하면 거래 생성 전 `JOINT_LOCK_BUSY` 409를 반환한다. 이 경우 해당 요청의 영수증이 아직 없는 것은 정상이다. 다른 콘텐츠·다른 기기·중복 화면의 동시 행동이 후보이며, 실제 관측 409의 상세 원인은 본문/계정 상관 정보 없이 확정할 수 없다.

개선 우선순위는 잠금 충돌과 응답 유실을 구분하고, 지연된 영수증을 제한된 횟수로 다시 확인하는 것이다. 명확히 미접수된 잠금 거절의 경우에도 기존 requestId와 멱등성 보장을 유지해야 한다. 불명확한 404만으로 pending을 삭제하거나 새 UUID로 구매를 반복해서는 안 된다. 기존 정책상 재입장은 GET만 수행하고 자동 구매를 재개하지 않으므로, 이를 변경하는 구현은 별도 범위로 다룬다.

## 증빙과 한계

- `tail-summary.json`: 실시간 표본과 지연 요약. Cloudflare tail의 단기 관측이며 클라이언트가 받기 전의 네트워크 유실은 포함하지 않는다.
- `db-summary.json`: 계정 범위·시간대별 처리량·연결/잠금 상태. 운영 데이터 변경 없음.
- `client-reproduction.json`: 실제 세션 모듈에 오류 응답을 주입한 읽기/POST 모의 재현.
- `source-verification.json`: 당시 Pages 소스 `63f48b789b776d76cdd9b68fee14f6ec7e22c045`, 배포 `3128b5ec`, 세션/계약실/통신 모듈의 운영 일치 해시.
- 과거 상세 HTTP 로그 조회 API는 현재 토큰에 조회 권한이 없어 403이었다. 집계 GraphQL과 실시간 tail로 대체했다. GraphQL의 Worker errors 0은 처리된 HTTP 409/503이 없다는 뜻이 아니므로 혼동하지 않는다.
- 사용자 기기의 저장 상태·오래 열린 구버전·특정 계정의 동시 동작은 직접 수집하지 않았다. 과거 대비 ‘이전 결과 확인’ 발생률 증가의 정확한 수치는 아직 확정할 수 없다.

진단 문서만 반영한다. 기능 테스트 전체 실행이나 운영 재배포는 하지 않는다.

# 군단토벌 운영 모드 · 0.1 가중치 · 실계정 보상

2026-09-28 사용자 요청: ON/OFF/TEST 설정, 드랍 후보 선택 가중치 0.1 단위. ON에 실계정 지급까지 연결하는 범위를 명시적으로 승인받았다.

## 운영 방식

| 모드 | 접근 | 보상 |
| --- | --- | --- |
| OFF | 모든 계정 이용 중지 | 신규 지급 차단 |
| TEST | OWNER 전용, 무제한 | 검수 기록만 저장 |
| ON | 일반 계정 하루 2회, OWNER 무제한 | 직접 주운 전리품을 즉시 계정에 지급 |

기존 `legion_hunt_settings_v1`의 mode 생략은 TEST로 해석한다. DB 마이그레이션과 자동 ON 전환이 없다. CMS 저장으로 모드는 즉시 적용하고 드랍 확률·후보·수량은 출전 시 고정한다. TEST에서 시작한 원정은 이후 ON 전환에도 실지급하지 않는다. ON 원정은 TEST/OFF 중 지급이 중지된다. 모드를 다시 ON으로 돌리더라도 만료된 전리품을 살리지 않는다. 이미 지급한 보상은 철수·취소 후에도 유지한다.

선택 가중치는 0~1,000,000, 소수 첫째 자리까지 허용한다. 사용 후보는 0보다 커야 한다. 추첨 시 가중치를 10배 정수로 변환해 0.1:0.9와 1:9를 동일하게 처리한다. 수량은 기존 정수 조건을 유지한다.

## 저장·부하

- 기존 `prepareUnifiedDropGrant`를 재사용해 인벤토리 아이템·카드·장비·이동수단을 각 보관함에 지급한다. 장비보호권 등 별도 경제 정책의 지급 제한은 공용 로직 그대로 유지한다. 이동수단 중복은 기존 차고 단일 소유 방식이며 추가 재화로 바꾸지 않는다.
- 보상 식별자는 `LEGION_HUNT:<원정 UUID>:<드랍 UUID>`. 기존 계정 세션 문서의 claim 결과가 지급 영수증이다. 사용자 락 안에서 session CAS, 설정/후보 유효성, 보상 변경, 지급 행수 검증, 영수증을 같은 DB batch에 저장한다. 고유 쓰기 토큰으로 동일 요청 동시 실행에서도 CAS 승리자를 구분한다.
- DB 실패·지급 0행·경합 시 모든 변경이 롤백된다. 응답 유실 후 같은 토큰으로 재시도하면 영수증만 반환하며 지급/세션 쓰기는 반복하지 않는다. 지급 수량·보상은 클라이언트에서 받지 않는다.
- PVE 메뉴가 만들어질 때 작은 status 조회 1회로 공개 여부를 결정한다. 전역 폴링·도감 전체 조회·덱 조회를 추가하지 않는다. 전투 요청은 설정 키와 본인 세션 키만 읽으며, 줍기 시 보상 해당 종류만 조회한다. 신규 테이블·인덱스·의존성·공통 DB 코드 변경이 없다.
- 부모 화면의 보관함 캐시는 실제 지급이 있었던 원정을 닫을 때 한 번 갱신한다. 드랍을 주울 때마다 메인 화면의 계정 재조회를 호출하지 않는다.

## 관련 검증

- 신규 서버/클라이언트 회귀 10개 통과: SQLite/PostgreSQL에서 모드 접근·일일 입장·4종 지급·응답 유실·중복 재시도·실패 롤백·지급 0행·세션 경합·모드 경합·TEST 원정 보호, 0.1 경계 추첨, 메뉴 상태 조회 횟수.
- 로컬 실제 CMS에서 ON과 0.1을 저장 후 재조회했다. PC와 모바일에서 모드 선택, 가중치 입력, 일반 계정 메뉴 및 일일 2회·실지급 안내를 확인했다. 테스트 사운드는 OFF다.
- 배포 검사: 기존 `tests/legion-hunt-owner-cms-20260926.test.mjs`, `tests/legion-hunt-entry-account-20260926.test.mjs`, `check:worker`. 신규 10개는 같은 실행 코드에서 이미 통과했으므로 배포에서 중복 실행하지 않는다.

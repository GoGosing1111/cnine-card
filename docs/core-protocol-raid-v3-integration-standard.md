# 코어 프로토콜 레이드 · PROJECT V V3 통합 규정

- 규정 ID: `PV-V3-RAID-INTEGRATION-1.1`
- 상태: 고정
- 확정일: 2026-08-30
- 적용 범위: 코어 프로토콜 및 이후 PROJECT V V3 전투엔진을 사용하는 신규 레이드

## 1. 소유권 경계

라이브 PROJECT V V3가 전투 화면의 단일 기준이다. 신규 레이드는 아래 항목을 복제·대체·재배치하지 않는다.

- 캐릭터 생성, 전신 비율, 진형 좌표와 반응형 배치
- 도감 카드 원화와 전투 SD를 선택하는 자산 해석
- 하단 로스터, 카드 프레임, 등급별 프레임과 카드 표기
- 전투 배경, 렌더러와 라이브 아트 어댑터 체인

기준 진입점은 `js/battle-v3-live.js`의 라이브 V3 실행 경로이며, 캐릭터·진형 구현 기준은 `preview/project-v-v3/source/battle/BattleEngine.js`와 `BattleCharacter.js`다. 신규 레이드가 별도 렌더러나 별도 카드 로스터를 만들지 않는다.

## 2. 신규 레이드가 추가할 수 있는 범위

신규 레이드는 기존 V3 전투 위에 다음 요소만 추가한다.

- 레이드 입장·작전 선택·공동 게이지 같은 전투 전후 화면
- 서버 타임라인의 기믹 이벤트와 단계 전환
- 연타, 순서 입력 등 QTE 오버레이
- 기믹 경고, 성공·실패 결과와 전투 복귀 UI

이 요소는 부가 계층이어야 한다. 기존 V3 캐릭터, 진형, 로스터, 카드 프레임, 판정 문구를 덮어쓰거나 DOM/CSS 선택자로 재스타일링하지 않는다.

## 3. 카드 원화와 전투 SD 계약

- 전투 하단 카드 도크는 라이브 V3 고정 영역이다. 마크업은 `js/battle-v3-live.js`의 `rosterCardHtml`, 비율·축소·배치는 `css/card.css`와 `css/battle-v3-live.css`, 등급 프레임은 라이브에서 로드하는 등급별 CSS·자산을 그대로 사용한다.
- 하단 카드 도크의 이미지에는 도감/카드목록에서 보이는 카드 원본만 표시한다. `battleSprite`, 전투 SD, 투명 전신 스프라이트를 카드 이미지로 표시하는 것은 금지한다.
- `ZENITH`는 `zenith-frame-concept-v2.png`, `SUPERSTAR`는 `superstar-championship-frame-v1.webp`, Faker 전용 카드는 기존 챔피언십 프레임 계층을 반드시 유지한다. 등급 프레임 이미지 계층을 생략하거나 신규 레이드 전용 프레임으로 교체하지 않는다.
- 프리뷰도 라이브와 동일하게 `cnineCardCatalog`의 원본 카드 → `originalCardArt`/`sourceArt` → 원본 `image` 순서로 하단 카드 이미지를 복원한다.
- 신규 레이드가 하단 카드 마크업, 프레임 DOM, 등급별 프레임, 카드 비율, 도크 위치를 자체 구현하거나 CSS로 덮어쓰지 않는다.
- `image` 또는 `sourceArt`는 카드·로스터 표시용 원화다.
- `battleSprite`는 전투 필드 캐릭터용 투명 SD다.
- 두 필드는 전송·정규화·렌더링 전 과정에서 분리한다.
- `battleSprite`가 있다는 이유로 `image`를 SD 경로로 덮어쓰지 않는다.
- 원화가 없는 경우의 대체 규칙은 라이브 V3 자산 어댑터가 담당한다. 신규 레이드가 임의 이미지를 주입하지 않는다.

## 4. 프리뷰 동등성

독립 프리뷰도 라이브와 동일한 V3 렌더러 및 아래 어댑터를 같은 순서로 로드한다.

1. `js/project-v-battle-art-adapter-v1.js`
2. `js/project-v-tier-battle-art-adapter-v1.js`
3. `js/project-v-monster-battle-art-adapter-v1.js`
4. `js/project-v-unassigned-battle-fallback-v1.js`

프리뷰 전용 가짜 카드, 가짜 등급·이름, 특정 카드 프레임을 강제로 부르는 ID를 사용하지 않는다. 프리뷰 샘플도 실제 형식의 `image`와 `battleSprite`를 각각 제공하며, SD를 카드 원화로 표시하지 않는다. 흰 마네킹이나 프레임 왜곡이 보이면 기믹 문제가 아니라 라이브 어댑터 체인 누락으로 우선 판정한다.

## 5. 변경 전 확인선

- 신규 레이드가 라이브 V3 진입점을 통해 실행되는가
- 서버 타임라인을 사용하더라도 렌더러는 기존 V3인가
- 신규 CSS가 `.card-frame`, V3 로스터 또는 Pixi 진형을 대상으로 하지 않는가
- 카드 원화와 `battleSprite`가 서로 다른 목적의 필드로 유지되는가
- 프리뷰와 라이브가 동일한 아트 어댑터 체인을 사용하는가
- 하단 카드가 라이브 `rosterCardHtml`과 공용 카드/등급 스타일을 사용하며 이미지가 도감 원본인가

이 확인선 중 하나라도 깨지면 라이브 이식 전에 수정한다.

## 6. 방 입장권과 삼중 코어 공명 규칙

- 공대 생성자는 `CORE_RAID_ENTRY_TICKET` 1장을 소모하고 참가자는 입장권을 소모하지 않는다. 인벤토리 대표 이미지는 `assets/items/core-raid-entry-ticket-v1.png`를 단일 기준으로 사용한다.
- 코어 진척은 전투 승리와 방향·연타 기믹을 모두 통과한 경우에만 서버가 계산한다.
- 세 코어의 현재 최고점과 최저점 차이를 공명 편차로 본다. 허용 편차는 `ceil(코어 목표 × coreBalanceTolerancePercent / 100)`이며 기본값은 34%다.
- 현재 최저점인 코어를 공략하면 균형 복구를 위해 일시적으로 허용 편차를 넘더라도 진척을 인정한다. 둘 이상이 최저점이면 모두 권장 대상으로 본다.
- 최저점이 아닌 앞선 코어를 더 올렸을 때 예상 편차가 허용치를 넘으면 `CORE_OVERLOAD`로 확정한다. 해당 시도의 코어 진척은 0으로 무효화하고 공대 HP에 `coreImbalanceDamage`를 적용한다. 기본 피해는 100이다.
- 세 코어가 모두 목표점에 도달하고 공명 균형 판정까지 통과해야 최종 보스 단계로 이동한다.
- 균형 판정, 과충전 피해와 보스 진입은 서버가 확정한다. 화면은 서버가 반환한 권장 코어·위험 코어·편차·안정도를 표시만 하며 클라이언트 값을 신뢰하지 않는다.
- 공개 상태는 별도 최종 승인 전까지 `TEST`, 보상은 잠금 상태를 유지한다.

# 리미티드 용병팩 확률 정밀도 확장 — 2026-10-10

기존 최소 0.0001%를 **0.00000001%**로 확장했다. CMS 입력·저장·검증, 확률 합계, 실제 서버 추첨과 공개 확률 표시가 같은 정밀도를 사용한다. 현재 운영 확률을 더 낮게 저장하거나 가격·한도·발행량·ON 상태를 변경하는 작업은 하지 않았다.

## 구현

- `shared/mercenary-limited-rates-v1.mjs`는 십진 입력을 정수로 변환하고 반올림 없이 소수점 최대 8자리 %로 표시한다. 음수·100% 초과·과도한 자릿수·비정상 숫자는 거부한다. 작은 값을 0이나 지수 표기로 축약하지 않는다.
- 기존 `rankRatesPpm`·`normalRankRatesPpm`·`chancePpm` JSON 필드와 단위를 유지한다. 1 ppm을 10,000개 정수 티켓으로 세분화하여 소수점 4자리 ppm을 지원한다. 예: `0.0001 ppm = 0.00000001% = 100억 티켓 중 1개`. 과거 정수 ppm 값은 수정·재저장 없이 그대로 읽는다. DB 스키마·공통 거래·일반 용병팩 단위는 변경하지 않았다.
- 모든 결과 확률을 정수 티켓으로 합산해 정확히 100%인지 확인한다. 합계가 한 티켓 차이여도 개봉을 막는다. 기존 정수 ppm 구성은 원래의 100만 티켓 경계를 사용하고, 미세 단위가 하나라도 있으면 100억 티켓을 사용한다.
- 리미티드팩 전용 RNG가 40비트 암호학적 난수를 만들고 나머지 연산 편향을 거부 표본추출로 제거한다. 모든 정수 계산은 JavaScript 안전 정수 범위다. 일반팩의 기존 RNG는 변경하지 않았다.
- 일반 6등급·리미티드 2등급·재료·꽝 입력이 같은 최소 단위를 지원한다. OWNER 관리 권한·버전 충돌·감사/재시도와 차감/지급/한도 원자성은 기존 경로를 유지한다. 확정된 이전 영수증은 다시 추첨하지 않는다.
- 유저용 “획득 확률과 최근 결과”와 공개 설정 API는 유지한다. 실제 저장된 확률을 최대 8자리로 그대로 표시한다. 별도 표시 확률·숨은 확률 필드는 없으며 공개값과 실제 추첨을 다르게 적용하지 않는다.
- CMS 및 팩 UI 진입 URL의 캐시 버전을 `20261010-precision`으로 갱신했다.

## 검증

새 회귀 5개가 통과했다. 최소값·최대값·기존값의 입력/JSON/표시 왕복, 한 티켓 합계 오류, 난수 양 끝값과 거부 후 재추출, SS 1티켓/SSS 2티켓/꽝 경계 및 0확률 제외를 확인했다. 실제 CMS 저장과 일반 유저 설정 API가 동일한 값인지 비교했다. 감사 실패 롤백, 미세 확률의 10회 지급 실패 롤백, 응답 유실·재시도 시 1회 차감/지급과 일련번호도 검사했다.

PC 1440×1000·모바일 390×844에서 실제 CMS/팩 UI 및 격리 PostgreSQL API로 `0.00000001%`, `0.00000002%`, `99.99999997%`를 저장·다시 불러왔다. 입력값과 유저 표시가 일치하고 합계 100%, 1회/10회 버튼 활성, 가로 넘침/JS 오류/누락 리소스 없음을 확인했다. 화면과 결과는 `docs/qa/mercenary-limited-precision-20261010/`에 보존했다. 검수 값은 운영에 저장하지 않았다.

기존 회귀 중 ppm 1.5를 무조건 거부하던 조건은 새 단위보다 세밀한 값 거부로 수정했다. 직접 추첨용 재고 검사 데이터는 확률 합계가 100%가 되도록 정리했다. 정상 가격/당첨률 기대값은 바꾸지 않았다.

## 배포 범위

작업 중 먼저 운영에 반영된 PWA 아이콘 및 S 후열 PVE 수정을 보존한다. 직전 실제 운영 커밋은 해당 배포 영수증의 `cfeceb1738704fd19b14961600777ca579ce0b20`다. 리미티드팩의 정밀도·표시·추첨에 한정된 변경이며 인증/DB 기반/의존성 구조 변경은 없다. 공식 `npm run deploy:production -- --scoped`로 기존 pack·mixed-pool·launch 회귀와 Worker 검사를 실행한다. 이미 통과한 신규 정밀도 5개와 PC/모바일 검사는 반복하지 않는다.

운영 반영 후 저장된 정책·팩 설정·리비전이 배포 전과 동일한지, 새 CMS/유저 JS·확률 모듈·진입 캐시가 실제 주소에 반영됐는지만 확인한다. 운영 저장·구매·지급은 수행하지 않는다. 새 미세 확률을 저장한 뒤 구형 코드로 되돌릴 때는 정밀도 지원을 유지해야 하며 저장값을 반올림해 복구하지 않는다.

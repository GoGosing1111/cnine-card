# 모든 OWNER 버닝·하이퍼 버닝 관리 권한 복구

2026-09-27 사용자 지시: `OWNER 전체 하이퍼버닝,버닝 권한 재 부여해`.

## 변경

- 기존 서버와 CMS는 `OWNER`이면서 닉네임이 `핑크빛유두`인 계정만 허용했다. 다른 OWNER가 조회할 때 403이 발생하는 회귀를 실제 API 분기 실행 테스트로 재현했다.
- `functions/_burning_event_access.js`와 `admin/burning-admin.js` 모두 인증된 `OWNER` 등급 기준으로 통일했다. 닉네임 변경·공백·누락과 무관하게 허용한다.
- `admin/burning-event`, `admin/hyper-burning-event`의 GET/PATCH에 동일 정책을 적용한다. 미인증은 401, 다른 등급은 403이며 이벤트 자료 조회·본문 처리·저장 이전에 차단한다.
- 안내 문구와 잠금 배지에서 특정 닉네임을 제거하고 CMS JS/CSS 쿼리 버전을 `20260927-all-owners`로 갱신했다.
- 기존 인증, 30/60/120분 타이머, 모드 상호 배제, 저장 트랜잭션, 실제 조작자 감사 로그를 유지한다. 운영 DB 직접 변경·사용자 등급 변경·이벤트 발동은 이 작업에 포함하지 않는다. 요청당 DB 조회와 왕복을 추가하지 않는다.

- 확인한 직전 운영 배포: `e24ab388-c4af-4c99-b50f-f15169acee5f`, 커밋 `06b82dd4c0e07fafeb0773d730513caa2367a75b` (Cloudflare Pages production 목록).
- 해당 배포 이후 원격 main에 있던 변경은 문서, `SSS 미승인본` 보존 자료와 승인된 X-BODY 독립 프리뷰이며, 이번 실행 코드 범위는 버닝 권한 함수·API 오류 문구·CMS JS/CSS/로더뿐이다.
- `test:burning`을 전체 게이트에 포함했다. 여러 OWNER의 두 API GET/PATCH 성공·감사 로그, 비OWNER·미인증 차단, 기존 타이머/기간/상호 배제, CMS 로더 버전을 검증한다.

## 출시 검사 중 발견한 기존 기록 불일치

- 첫 배포 시도에서 버닝 관련 11개 검사는 통과했으나 V3 공용 번들 최신성 검사가 중단시켰다. 기존 등록 작업에서 베르칸·크라이베른·저격 오리꿍 공유 모듈의 소스 해시가 빌드 기록에 반영되지 않은 상태였다.
- 지정 빌더 `npm run build:v3-grid`로 재생성한 결과 실제 9개 전투 번들·레이아웃 번들의 내용은 동일했고 `grid-build-report.json`의 소스 해시 3개만 갱신됐다. 게임 전투 코드·자산 변경 없이 검증 기록을 일치시켰다.
- 첫 시도는 운영 업로드 전에 중단됐다. 갱신한 기록을 범위 커밋한 뒤 지정 배포 명령으로 전체 검사를 다시 진행한다.
- 이어서 구형 스킬 밸런스 회귀가 베르칸 등록 전 34종을 기대하는 불일치를 확인했다. 현재 CMS 기준 35종으로 맞추고 베르칸의 별도 승인 밸런스를 보존하는 검증을 추가했다. 밸런스 실행 코드와 운영 수치는 수정하지 않았다.
- 인접 카탈로그 회귀의 원화 개수도 베르칸 포함 55종으로 바로잡았다. 저장 문서 revision 54는 별도 값이므로 유지했고 베르칸 존재 검사도 추가했다. 이 불일치를 확인한 세 번째 검사 실행은 운영 업로드 전에 중단한 뒤 수정했다.
- 기존 라그니엘 획득 회귀는 SSS 전체에 베르칸이 추가된 뒤에도 총 가중치 10,000을 가정했다. 해당 테스트와 인접 가중치 테스트에서 베르칸을 명시적으로 제외해 과거 시험 시나리오를 고정했다. 크라이베른 후보 회귀의 독립 스킬 목록 개수는 현재 35종으로 맞추었다. 이는 메모리 테스트 설정만의 변경이며 실제 운영 확률·획득 스위치는 그대로다.
- 같은 카탈로그를 읽는 의상·무기 회귀도 55종 집계와 최신 V-055 정렬로 맞췄다. 전체 게이트에 연결된 나머지 테스트에서 같은 구형 34/54종 개수 가정을 찾아 인접 범위를 확인했다.

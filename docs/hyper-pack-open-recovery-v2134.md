# 하이퍼팩 v2134 장애 원인·수정·검증·배포 기록

기록일: 2026-09-22, 한국 시간(KST).

**공통 개봉 잠금·로딩 개선은 운영에 배포했다. 후속 신고에서는 오메가-X의 JPG 원화를 결과 검사에서 거부하는 별도 결함을 확인했다. 동일한 운영 영수증으로 실패를 재현했고, 수정 후보에서 복구·다음 개봉 요청을 확인했다. 후속 수정의 운영 배포 결과는 7절에 기록한다.**

이 문서에서 영수증은 서버에 저장된 개봉 요청 번호·횟수·당첨 결과·차감 내역을 뜻한다. 인계 문서의 원인 분석은 기준 코드와 대조했고, 성능 추정치는 이번에 직접 측정한 결과와 구분했다.

## 1. 신고 증상과 확인한 원인

최초 신고는 “하이퍼팩 개봉이 느리고, 이전 개봉 처리 확인을 눌러도 반응이 없다”였다. 핵심은 **지급 처리와 화면 연출이 하나의 클라이언트 잠금을 공유하던 구조**였다.

| 문제 | 이전 동작과 영향 | v2134 변경 |
|---|---|---|
| 지급 완료 후에도 개봉 잠금 유지 | `open()`이 연출 완료까지 기다린 뒤 `finally`에서 `busy=false`를 실행했다. 보상을 이미 지급했어도 연출 중에는 개봉·복구가 잠겼다. | 영수증 저장과 지급 완료 이벤트 직후 잠금을 해제하고, 이후 연출을 실행한다. |
| 이미지 로딩 무한 대기 | `Assets.load`가 끝나지 않으면 연출을 기다리는 호출도 끝나지 않아 잠금 해제에 도달하지 못했다. | 연출 준비·재생에 제한 시간을 두고, 실패하면 저장된 전체 결과를 표시한다. |

| 재개봉 호출 순서가 잠금과 결합 | 결과창을 닫는 코드가 재개봉 콜백을 즉시 호출했다. 잠금 정리가 늦어지는 상황과 분리되지 않았다. | 결과창을 먼저 닫고 다음 마이크로태스크에서 재개봉한다. 이전 요청의 늦은 종료가 다음 요청의 잠금을 풀 수 없게 했다. |
| 개봉 전 원화 대량 다운로드 | 연출 시작 전에 당첨 용병의 큰 원본 이미지를 모두 불러왔다. 라이브에서 쓰지 않는 예시 원화도 준비 자산에 포함됐다. | 기존 도감용 640 WebP를 우선 사용하고, 라이브에서 예시 원화 로딩을 제외했다. |

| 서버 준비 상태 중복 조회 | 준비 단계와 커밋 직전에 같은 CMS·확률·재료 준비 검사를 반복했고, 테이블 존재 확인 6쿼리도 실제 개봉마다 실행했다. | 실제 개봉에서는 존재 확인을 생략하고, 커밋 직전에는 개봉 ON/OFF를 다시 확인한다. |
| 영수증의 순차 조회 | 당첨 용병마다 획득 기록을 한 번씩 읽어 최대 10개의 추가 순차 조회가 발생했다. | 해당 계정·요청의 획득 기록을 한 번에 읽어 원래 뽑기 순서로 결합한다. |
| 오메가-X 결과를 읽지 못함 | 원화 검사가 PNG·WebP만 허용하여 정식 JPG 원화가 포함된 완료 영수증을 거부했다. 로컬 미완료 기록이 남아 이후 개봉도 같은 오류를 반복했다. | 후속 수정에서 JPG·JPEG를 허용하고 실제 등록된 용병 47종의 결과 검사를 추가했다. |

### 지급 처리와 연출의 경계

```text
이전: 요청 잠금 → 서버 차감·지급 → 영수증 저장 → 연출 준비·재생 대기 → 잠금 해제
변경: 요청 잠금 → 서버 차감·지급 → 영수증 저장 → 잠금 해제 → 연출 준비·재생
                                                              └ 실패 시 저장된 결과 표시
```

일반 결과창은 계속 `showModal()`을 사용한다. 결과창 뒤의 버튼을 연출 중에 직접 누를 수 있다는 의미는 아니다. **거래 잠금 해제**와 **모달의 배경 조작 제한**은 서로 다른 동작이다. 닫기·결과 확인 후 복구와 다음 개봉이 이어지는지를 검증했다.

## 2. 클라이언트 수정 상세

대상: [mercenary-pack-live.mjs](../js/mercenary-pack-live.mjs)의 `open`, `showMercenaryReceipt`, `accountFlags`, `requestSync`.

### 2.1 요청별 잠금 해제

- `completeReceipt()`가 요청 번호와 횟수를 검증하고 최근 영수증을 저장한 다음, 지급 완료 이벤트를 보낸 뒤 `release()`를 호출한다.
- `release()`는 요청별 `released` 값을 사용해 한 번만 실행한다. 오류 경로의 `finally`에서도 같은 함수를 호출한다.
- 이 장치가 없으면 첫 요청의 연출이 늦게 끝났을 때, 이미 진행 중인 두 번째 요청의 잠금을 잘못 해제할 수 있다. 이 순서를 직접 재현하는 회귀 테스트를 추가했다.
- 잠금 중 재시도에는 `이전 개봉 요청을 처리하고 있습니다. 잠시 후 다시 확인해 주세요.`를 표시한다.
- 재개봉 버튼은 중복 클릭을 막고 결과창을 닫은 다음 `Promise.resolve().then(onRepeat)`로 다음 요청을 시작한다.

### 2.2 연출 실패 시 결과 보존

| 단계 | 제한 시간 | 초과 시 표시 |
|---|---:|---|
| 연출 스크립트 로딩 | 기존 15초 유지 | 개봉 연출을 불러오지 못했습니다. |
| `fx.init()` | 20초 | 개봉 연출 자원을 불러오지 못했습니다. |
| `fx.play(results)` | 20초 + 장당 12초 | 개봉 연출이 응답하지 않습니다. |

재생 제한은 1회 개봉 32초, 10회 개봉 140초다. 준비 단계와 별도이며 전체 개봉 API의 제한 시간이 아니다.

실패하면 `MERCENARY_PACK_FX_FAILED`와 실제 오류를 콘솔에 남기고, 상태줄에도 안내한다. 연출 인스턴스를 정리하고 무대만 숨기며 이미 만들어 둔 결과 목록을 유지한다. 일시정지·건너뛰기 버튼은 비활성화하고 재개봉 버튼은 거래·운영 상태에 따라 다시 활성화한다.

`Promise.race`에 의한 대기 종료이므로 **진행 중인 Pixi 이미지 네트워크 요청 자체를 중단하는 구현은 아니다.** 기존 인스턴스 폐기·세대 검사와 함께 늦게 끝난 연출이 화면을 다시 점유하지 않도록 처리한다. 재생 제한 시간은 실제 경과 시간 기준이므로 일시정지 시간도 포함한다.

### 2.3 계정 상태 캐시와 갱신

캐시에는 `accountId`, 미완료 요청 유무, 최근 영수증 유무만 저장한다. 계정 전체를 별도로 복제하지 않는다.

- 자체 영수증·미완료 요청 저장/삭제, 개봉 시작/잠금 해제 시 캐시를 무효화한다.
- `cnine:account-mutation`, `storage`, 화면 복귀·포커스·가시성 갱신에서 상태를 다시 읽는다.
- **인계 패치에 추가한 보완:** `cnine:player-updated`도 처리한다. 실제 `app.js`의 로그인·프로필 저장은 이 이벤트를 사용하고, 같은 탭의 저장은 `storage` 이벤트를 발생시키지 않기 때문이다.
- DOM 변경은 `requestAnimationFrame`으로 합친다. 100번의 관찰자 호출이 한 프레임의 갱신으로 모이고, 계정 변경이 없으면 `loadUser()`를 다시 호출하지 않는 테스트를 추가했다.

## 3. 이미지와 캐시 개선

대상: [하이퍼팩 FX 소스](../js/hyper-pack-fx-v2076.src.js), [전용 번들](../js/hyper-pack-fx-v2076.bundle.js), [하이퍼팩 CSS](../css/hyper-pack-v2076.css).

- 연출과 결과 목록 모두 `/assets/ui/project-v/mercenaries/codex-v1/<code>-art-640.webp`를 우선 사용한다.
- 경량 이미지가 실패할 때만 원본 `sourceArt`로 대체한다. 결과 목록은 `loading="lazy"`, `decoding="async"`를 사용한다.
- 연출은 성공한 이미지 경로를 인스턴스의 `Map`에 보관하고 종료 시 비운다. 도감·다른 화면에서 사용하는 원본은 수정하거나 재압축하지 않았다.
- 라이브 초기 준비 자산은 팩·에너지·프레임 3개다. 프리뷰는 예시 원화를 포함한 기존 4개를 유지한다.

| 측정 대상 | 결과 | 해석 |

현재도 공용 팩 PNG 2,320,469바이트, 에너지 PNG 1,538,242바이트, 프레임 PNG 1,385,157바이트와 벤더 번들 661,177바이트가 남아 있다. 따라서 인계 문서의 **“전체 최초 로딩 1MB 미만”을 달성했다고 기록하지 않는다.** 파일 크기 합계와 캐시·압축이 반영되는 실제 네트워크 전송량도 구분한다.

### 3.2 캐시 버전과 표시

- 메인 및 동적 import의 하이퍼팩 모듈: `v=2134-open-lock`.
- 메인 `app.js` 참조의 `hyper` 파라미터: `2134-open-lock`. 다른 파라미터는 유지했다.
- 하이퍼팩 CSS: `v=2134-recover-state`. 메인과 관리자 화면에 함께 반영했다.
- FX 번들: `v=2134`, 런타임 버전 확인도 `>=2134`로 맞췄다.
- 복구 버튼에 스타일·최소 높이·`aria-busy`를 추가했고, 개봉 OFF·요청 처리 중 상태를 시각적으로 구분했다.
- 최종 변경에는 공용 V3 전투 번들, 공용 벤더 번들, 서비스워커의 전투 버전 변경이 포함되지 않았다. 전용 번들 빌드 과정에서 생성된 공용 벤더 차이는 최종 변경에서 제외했다.

## 4. 서버 조회 최적화와 지급 일관성

대상: [개봉 정책](../functions/_hyper_pack_opening.js), [용병 계정 처리](../functions/_mercenary_account.js).

### 4.1 준비 상태 검사 중복 제거

`hyperOpeningReadiness(env, {probeTables=true})`를 도입했다. 관리자 상태 조회와 ON 전환 검사는 기존처럼 테이블 존재 확인을 수행한다. 실제 개봉 경로는 `probeTables:false`를 사용한다.

`hyperOpeningRuntime(env, {recheck:true})`는 커밋 직전 ON/OFF를 다시 읽는다. 같은 요청의 준비 단계에서 확인한 CMS·확률·재료 준비 조회를 반복하지 않는다.

**원자적 ON/OFF 검사는 유지했다.** `hyperOpeningGuards`의 PostgreSQL 행 잠금과 정책 원문 일치 검사는 차감·지급과 같은 트랜잭션에 들어간다. 운영자가 OFF로 전환했을 때 클라이언트 버튼 상태만 믿고 개봉을 허용하는 변경이 아니다.

### 4.2 영수증 획득 기록 일괄 조회

`mercenaryOpeningReceipt()`는 해당 요청에서 용병을 뽑은 위치의 획득 ID만 모아 계정 조건과 `IN (...)`으로 한 번 조회한다. 결과를 ID로 연결해 원래 뽑기 순서를 유지한다. 용병이 한 장도 없으면 획득 기록 조회도 하지 않는다.

10장 모두 용병인 경우, 코드 구조상 영수증 관련 조회는 **요청 기록 1회 + 획득 기록 10회에서 요청 기록 1회 + 획득 기록 1회**로 줄어든다. 이는 해당 함수의 조회 수 비교이며 개봉 전체 API 쿼리 수가 아니다.

획득 행이 없으면 중복 여부·누적 수량을 임의로 만들지 않는다. SQLite와 PostgreSQL 테스트에서 획득 행 하나를 지운 뒤, 그 위치의 메타데이터는 비워 두고 나머지 순서와 수량이 유지되는지 확인했다.

### 4.3 유지한 경제 동작

- 완료된 요청을 다시 조회할 때 같은 결과를 사용하며 새 차감·새 추첨을 하지 않는다.
- 응답을 잃어버린 미완료 요청은 기존 요청 번호로 재시도한다. 불확실한 요청을 무조건 삭제하지 않는다.
- 요청 번호·개봉 횟수와 서버 결과가 다르면 미완료 기록을 유지하고 오류를 표시한다.
- 1회 5억 코인, 최대 10회, 운영 확률, 등급, 개별 보장 설정과 사용자의 기존 보유 수량은 이번 패치로 변경하지 않았다.
- 검증을 위해 운영 계정에 새 개봉·차감·보상 지급을 실행하지 않았다.

| 회귀 | 확인 내용 |

| 지연된 첫 연출 + 진행 중인 두 번째 요청 | 첫 요청의 늦은 완료가 두 번째 거래의 잠금을 해제하지 않는다. |
| 빠른 중복 클릭 | POST를 하나만 보내고 처리 중 안내를 표시한다. |
| DOM 변경 100회 | 프레임 갱신 1회, 변경 없는 계정 재파싱 0회 |

| 다른 탭 영수증 저장 | `storage` 이벤트 뒤 최근 개봉 결과 버튼으로 갱신한다. |
| 획득 행 일괄 조회·누락 | 두 DB 호환 경로에서 조회 1회·뽑기 순서·누락 메타데이터 보존을 확인한다. |

테스트 파일: [클라이언트 회귀](../tests/hyper-opening-ui-v2097.test.mjs), [계정·영수증 회귀](../tests/mercenary-account-v3.test.mjs).

최종 `release:gate` 로그의 테스트 실행 건수 합계는 **2,131건, 실패 0건**이다. 여러 스위트의 실행 수를 합산한 값이며 고유 테스트 이름 2,131개를 의미하지는 않는다. 비동기 DOM 갱신 테스트는 한 틱을 기다리도록 하네스를 수정했으며 기존 상태 검증을 제거하지 않았다.

### 5.2 테스트 DB와 실제 브라우저

Chrome 1440px·390px에서 실제 클라이언트와 서버 핸들러를 PostgreSQL 호환 테스트 DB(PGlite)에 연결했다. 테스트 계정·확률을 사용하는 환경으로 운영 계정의 신규 개봉과 구분한다.

- 10회 개봉 → 10회 추가 개봉 → 닫기 → 최근 결과 복구를 확인했다. 총 POST 2회였고 복구로 추가 차감되지 않았다.
- 개봉 OFF 버튼의 흐린 표시, 모바일 결과 목록 스크롤과 이미지 표시를 확인했다.
- 자원 지연을 넣어 초기화 시간 초과 후 결과 목록·재개봉 경로가 유지되는지 확인했다. 이 시나리오는 20초 타이머를 테스트에서 300ms로 줄인 장애 주입 검사다.
- WebP를 404로 응답시켜 원본 대체를 확인했다. 정상 시나리오의 자원 오류·페이지 JavaScript 오류는 없었다.
- 인위적인 WebP 실패 시나리오에서는 예상한 대체 경고 외에 Pixi의 바인딩된 텍스처 폐기 경고 2종이 관찰됐다. 페이지 JavaScript 오류는 없었지만, 모든 콘솔 경고가 제거됐다고 보고하지 않는다.

### 5.3 운영 DB 읽기 전용 검사

`BEGIN READ ONLY`에서 운영의 완료된 10회 개봉 영수증 하나를 조회하고 `ROLLBACK`으로 종료했다.

| 항목 | 직접 확인한 값 |
|---|---:|
| 결과 수 / 용병 결과 수 | 10건 / 2건 |
| 영수증 함수 조회 수 | 2쿼리 |
| 그중 획득 기록 조회 | 1쿼리 |
| 영수증 함수 소요 시간 | 78ms |
| 준비 정책 조회 / 커밋 전 정책 재확인 | 5쿼리 / 1쿼리 |

78ms는 **해당 완료 영수증을 읽는 함수의 한 번 측정값**이다. 사용자 클릭부터 신규 결제·연출까지의 시간이나 개선 전후 비교값이 아니다. 인계 문서의 “약 45회 DB 왕복·약 2초”는 다른 API의 왕복 시간으로 추산한 값으로, 이번 운영 측정 결과로 승격하지 않는다.

### 5.4 운영 배포물 검사

배포 후 실제 운영 URL에서 하이퍼팩 모듈·전용 번들·CSS·`app.js`를 내려받아 검토한 로컬 내용과 비교했다. 4개 모두 HTTP 200이며 줄바꿈 정규화 후 내용이 일치했다. 메인 HTML의 캐시 태그와 개봉 ON·1회 5억·최대 10회 응답도 확인했다.

운영 자산을 사용한 브라우저 검사에서는 이미 읽은 운영 영수증으로 결과 10건을 렌더링했다. 상태·영수증 GET 응답은 검사 도구가 제공했고, 신규 POST는 허용하지 않았다. **로그인한 실사용자의 운영 신규 개봉을 끝까지 실행한 검사는 아니다.** 1440px·390px에서 닫기·복구 버튼, WebP HTTP 200, JavaScript 오류 0건을 확인했다.

저장된 결과의 첫 연출 상태까지 측정은 각각 1,380ms·2,811ms였다. 개봉 결제 시간이 포함되지 않았고 네트워크를 통제한 성능 비교도 아니므로 체감 속도 보장값으로 사용하지 않는다.

## 7. 배포 후 특정 계정 신고: 오메가-X JPG 결과 거부

사용자가 배포 후 특정 계정에서 계속 개봉되지 않는다고 신고했다. 이 신고는 공통 개선의 자동 검사 통과만으로 종결하지 않는다.

운영 DB에서 정확히 일치하는 계정을 찾아 다음을 읽기 전용으로 확인했다.

- 계정은 활성 상태이고 10회 개봉에 필요한 잔액이 있었다. 개봉 정책은 ON이었다.
- 계정 상태 함수와 최근 영수증 조회는 정상 응답했다.
- 마지막 개봉은 **2026-09-22 01:15:21 KST, 10회, COMPLETED**였다. 최근 20건도 모두 완료였다.
- 해당 계정의 전체 미완료·취소 개봉 요청 조회는 0건이었다. DB 기반 계정 잠금 행도 없었다. 이 결과만으로 별도 Durable Object의 순간적인 잠금까지 없다고 단정하지 않는다.
- 개인 감옥 기록은 비활성이었고, 1회 보장 설정을 읽는 경로에서도 오류가 없었다. 초기 조회는 전체 API 게이트·포로수용소 제한을 대신 검증한 것은 아니다.

그 계정의 실제 완료 영수증을 별도 브라우저에 제공해, 이전 완료 요청이 로컬 미완료 목록에 남은 상황을 재현했다. 1440px·390px에서 복구 결과 10건 표시, 로컬 미완료 기록 해제, `최근 개봉 결과` 표시 전환, 다음 10회 개봉 POST를 만드는 단계까지 정상 동작했다. 신규 POST는 검사 도구에서 차단해 운영에 전달하지 않았다.

### 7.1 결정적인 오류와 원인

사용자는 새로고침 뒤에도 무반응이라고 답했고, 첨부 화면에 `이전 개봉 처리 확인` 버튼과 **`용병 원화와 등급을 확인하세요.`** 오류가 함께 표시됐다. 해당 문구는 [결과 계약 검사](../shared/mercenary-pack-contract-v1.mjs)의 `mercenaryPackResults()`에서만 발생하는 문구다.

등록된 원화 47종을 이 검사에 모두 넣었을 때 **오메가-X(V-021) 한 종만 실패**했다. 정식 원화 `assets/ui/project-v/mercenaries/mercenary-v021-omega-x-source-art-v1.jpg`가 JPG인데, 검사식은 `png|webp`만 허용했다. SSS 등급이나 용병 코드가 잘못된 문제가 아니었다.

해당 계정의 **2026-09-21 23:48:24 KST** 완료된 10회 개봉에서 오메가-X 결과를 읽어 동일한 오류를 재현했다. 서버 거래는 `COMPLETED`이고 정상 지급됐지만, 클라이언트가 결과 검증 단계에서 중단되어 로컬 미완료 기록을 지우지 못했다. 이후 개봉 버튼도 같은 이전 결과를 먼저 검사하므로 계속 실패했다.

```text
오메가-X 지급 완료 → 서버 영수증 정상 → JPG 원화 검사 실패
                                       └ 로컬 미완료 기록 유지
다음 개봉/이전 처리 확인 → 동일 영수증 검사 → 동일 오류 반복
```

초기 조사에서 확인한 **가장 최근 영수증에는 오메가-X가 없었다.** 최신 완료 결과를 복구하는 검사는 통과했지만 사용자의 브라우저에 남은 더 오래된 오메가 결과를 대표하지 못했다. 최초 회귀 검사도 정식 카탈로그 전체 원화 형식을 검증하지 않아 이 누락을 잡지 못했다. 이번 오류를 단순 캐시 문제나 계정 잔액 문제로 기록하지 않는다.

### 7.2 후속 수정 범위

- 원화의 허용 확장자를 `png|webp|jpe?g`로 확대했다. 정식 JPG 원본을 변환하거나 덮어쓰지 않는다.
- 같은 용병 자산 디렉터리 제한, 외부 URL 차단, `..` 경로 이동 차단, 코드·등급·수량 검사를 유지한다.
- 메인 HTML·상점 동적 import·결과 계약 import의 캐시 식별자를 `2134-receipt-art-v2`로 맞춰 수정된 검사 코드가 로드되게 했다. 전투 번들·전투 버전은 변경하지 않았다.
- 완료된 영수증은 기존 요청 번호로 조회하여 복구한다. 운영의 코인·획득 기록·보장 확률을 수정하거나 미완료 로컬 기록을 무조건 삭제하지 않는다.

### 7.3 후속 검증과 배포 상태

새 회귀 테스트 2개는 수정 전 실패하고 수정 후 통과했다. 기존 관련 회귀를 함께 실행한 결과 **16건 통과, 실패 0건**이었다.

1. 실제 등록된 원화 47종 전체를 결과 검사에 통과시킨다. JPG·JPEG를 허용하되 외부 경로·경로 이동·SVG·잘못된 등급은 계속 거부한다.
2. JPG 오메가가 들어 있는 과거 10회 결과를 복구할 때 POST·추가 차감 없이 미완료 기록이 해제되고, 다음 10회 개봉은 새 요청 번호를 사용한다.

운영에서 읽은 오메가 영수증을 실제 운영 상점 HTML·JS에 제공한 브라우저 검사에서는 수정 전 동일 오류와 미완료 기록 유지가 재현됐다. 수정 후보를 적용한 Chrome 1440px·390px에서는 결과 10건, 오메가 WebP HTTP 200, 로컬 미완료 해제, `최근 개봉 결과` 전환, 다음 10회 POST 생성까지 확인했고 JavaScript 오류는 없었다. POST는 검사 도구에서 차단하여 운영 계정에 전달하지 않았다.

후속 수정은 정식 출시 게이트 및 운영 재배포 대기 상태다. 검사가 제공한 인증·상태 응답을 사용하는 재현이며, 사용자의 실제 기기에서 신규 결제까지 완료했다는 의미는 아니다.

## 9. 증거 보관

배포 트리 밖의 QA 디렉터리에 `browser-report.json`, `production-smoke.json`, `heeya-readonly-browser.json`, `heeya-store-browser.json`, `omega-before-report.json`, `omega-candidate-report.json`, 읽기 전용 조사 스크립트, 브라우저 캡처를 보관한다. 상위 작업 디렉터리의 `deploy.log`에는 최초 출시 게이트와 배포 결과가 있다.

개별 계정 번호·요청 번호·전체 영수증·세션 정보는 공개 변경 기록에 복사하지 않는다. 후속 수정의 최종 배포 결과는 7절에 이어 기록한다.

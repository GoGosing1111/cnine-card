# 랭크 듀오 갱신 대기·자동 입장 — 2026-09-27

사용자 지시: 최신 반영 안내 때문에 멈추지 않게 하고, 상대 매칭이 완료되면 추가 클릭 없이 바로 입장한다.

## 수정

- 전력 캐시를 다른 요청이 갱신 중이면 즉시 `DUO_PROFILE_BUILDING`으로 중단하던 경로를 수정했다. 이번 요청이 확보한 계정만 일괄 갱신하고, 다른 요청의 갱신 결과는 계정 인덱스 조회로 받는다. 중복 보유 목록 스캔과 부분 임대권의 상호 포기를 막는다.
- 한 서버 요청의 대기는 200/400/800/1,600ms, 최대 4회다. DB 트랜잭션 밖에서 기다리고 종료 시 자기 임대권만 해제한다. 갱신 중 덱 변경도 같은 제한 안에서 이어 처리한다.
- 매칭 뒤 수동 전투 시작 버튼을 제거했다. 전장 로딩은 매칭과 함께 시작하며, 티켓을 받으면 즉시 전투 요청과 재생으로 이어진다.
- 브라우저는 동일 티켓·요청 ID를 유지하며 갱신 경합, 일시적 서버 오류, 응답 유실과 `PENDING` 결과를 자동으로 이어 처리한다. 최대 24회, 새 요청 시작 기한 45초이며 개별 API의 기존 30초 제한은 유지한다. 화면을 떠나면 후속 요청을 중단한다. 장기 장애에서는 저장된 경기로 재진입할 수 있다.
- 저장된 진행 경기 또는 서버가 알려준 진행 경기는 화면 진입 시 자동으로 복구한다. 덱 자체가 잘못됐거나 행동력이 부족한 오류는 반복 요청하지 않는다.
- 모바일 검수에서 네 사람의 카드 목록이 결과창을 화면 위로 밀어 복귀 버튼이 잘리는 기존 문제도 발견했다. 듀오 결과창만 화면 중앙과 화면 높이 기준으로 제한해 결과·복귀 버튼을 표시한다.
- 매 경기의 실제 현재 편성·버전 검증, 개인 행동력 차감, 점수·보상의 기존 원자적 거래를 유지한다. 운영 정책·재화·시즌 데이터 변경 없음.

## 검증

- 신규 회귀: 한 번의 매칭 동작으로 전투 요청, 갱신 경합 자동 재시도, 같은 ID 유지, 응답 유실/진행 경기 복구, 유한 재시도, 화면 이탈, 잘못된 덱·부족 행동력·취소 처리, 실제 정산 장애와 버전 충돌 후 단일 차감.
- SQLite/Postgres pipeline 동시 갱신: 변경 계정 3명이 겹치는 요청 2개에서 보유 목록 조회 2묶음, 캐시 대기 1회, 임대권 잔여 0개. 관측 문장 수는 SQLite 35개/Postgres pipeline 18개이며 전체 참가자나 보유 목록을 재집계하지 않는다. 시험의 실행 시간은 테스트 진단 출력에 기록한다. 운영 부하 수치로 해석하지 않는다.
- 기존 듀오 서버/일괄 편성/승리 보상 회귀와 실제 배포 번들·메인 로더 연결 검사를 선택한다. 신규 회귀를 `test:ranked-duo`에도 연결한다.
- 로컬 QA 서버의 `/__duo-login`에서 운영 `index.html?screen=duo`와 실제 `js/app.js`를 사용한다. 전투 핸들러는 분리된 메모리 DB를 사용하며 운영 계정에 접속하지 않는다. `retry=1`은 프로필 경합과 정산 완료 응답 유실을 각각 한 번 주입한다.
- PC 1440×960: 실제 메인 앱 매칭 버튼 1회 → V3 전투 → 결과 → 듀오 로비 복귀, 행동력 10→9 확인.
- 모바일 390×844: 실제 메인 앱에서 경합·응답 유실 주입 후 버튼을 다시 누르지 않고 자동 입장했다. 결과·복귀 버튼의 잘림 보정 후 다시 입장·결과·복귀했고, 경기마다 행동력 1과 QA 승리 보상 250,000 코인만 처리됐다. 최종 결과창은 세로 195~649px, 복귀 버튼은 576~624px 안에 들어오며 브라우저 오류 0개다.

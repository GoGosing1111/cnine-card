사용자가 명함 로딩 화면을 첨부하고 “되게 느려 개선해”라고 요청했다. 새 리치왕 트로피의 과거 기록 조회가 명함을 열 때마다 모든 CLEAR 방의 대형 전투 JSON을 반복 파싱하는 원인이었다. 최초 검수의 작은 DB fixture와 예시 명함은 이 실제 데이터 크기를 재현하지 못했다.

## 실제 측정과 수정

- 운영 DB에 CLEAR 방 293건, JSON 합계 128,895,827바이트가 있었다. 기존 호환 JSON 함수와 배열 탐색을 이용한 해당 계정의 리치왕 집계 한 번이 **9,036ms**였다.
- 공식 ON 성공과 참여 증거만 추출해 **284건·146계정**의 기존 횟수를 한 번 이관했다. `scripts/ops/lich-trophy-baseline-20261011.mjs`는 JSON을 한 번씩 파싱해 필요한 참여 증거만 반환하며, 사용자별 영구 카운터와 완료 마커를 같은 거래에서 저장한다. 전체 재생 로그와 개인 인벤토리는 가져오지 않는다.
- 기존 카운터가 있으면 덮어쓰지 않고 확인된 과거 성공 이상을 포함하는지 검증한다. 신규 클리어와 같은 계정 순서로 잠그며 동시 클리어의 조건부 갱신 재시도를 유지한다. 재실행은 완료 마커로 무변경 처리한다. 오류는 이관 전체를 롤백하고 응답 유실 후 재시도도 중복 집계하지 않는다.
- 운영 dry-run 롤백 후 2026-10-11 **06:10 KST**에 실제 집계를 반영했다. 신규 카운터 146개, 기존 카운터 보존 0개였고 성공 횟수·달성일만 저장했다. 재화·전투 보상·플레이 상태를 변경하지 않았다.
- 완료 마커가 있으면 명함은 계정별 카운터만 읽는다. 과거 정벌이 없는 계정도 대형 재생 기록을 조회하지 않고 0을 반환한다. 신규 성공 횟수는 기존 클리어 트랜잭션에서 증가한다. 마커가 없는 개발/이전 환경은 기존 검증 가능한 기록 조회를 유지한다.
- 변경 후 리치왕 기록 조회: 기존 참가자 **76ms**, 정벌 기록 없는 계정 **147ms**. 실제 명함 핸들러의 운영 DB 읽기 전체는 두 계정에서 **1,623ms / 1,622ms**, 8종 트로피를 반환했다. 이 수치는 HTTP·인증·연결 수립을 제외하며, 계정 레벨은 이미 초기화된 스키마의 같은 읽기만 호출했다. 브라우저 총 체감시간을 이 수치와 동일하다고 주장하지 않는다.

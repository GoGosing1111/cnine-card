# 폐차장·무한의탑 연속 전투 정지 수정

## 원인

2026-09-13 운영 화면의 `TURN/KO 연출이 지연되어 다음 행동으로 이동했습니다`를 실제 서버 전투 생성기와 일반 계정 수준의 카드·배틀슈트·스킬칩으로 재현했다. 이전 검수의 고전투력·배틀슈트 미장착 조건으로는 발견하지 못했다.

- 라이브 연결부가 연속 전투를 한 이벤트씩 `playEvents([event])`로 넘겼다.
- 연속 엔진도 각 이벤트를 다시 분리했다. `V3_COMBAT_MS_V1`이 붙은 이벤트마다 스킬칩 재생기가 새로 만들어져, 절대 시각 `combatAtMs`까지 0초부터 다시 기다렸다.
- 바깥의 2초 제한이 정상 재생과 탄착 대기까지 실패로 취급하고 애니메이션·스킬칩·탄착 큐를 취소했다. 이후 이벤트도 같은 현상을 반복했다.

## 수정 계약

- `js/battle-v3-live.js`는 연속 전투의 전체 서버 타임라인을 한 번에 전달한다. 연속 전투의 배치·행동에는 기존 2초 생략 처리를 적용하지 않는다. 실제 실패는 호출자에게 전달하여 저장된 전투 기록으로 복구할 수 있게 한다.
- `ScrapyardBattleEngine.js`는 타임라인을 분리하기 전에 공용 스킬칩 재생기로 전달한다. 내부 재생은 `timedInternal`을 유지하여 시계를 재생성하지 않는다.
- 공용 `BattleSuitSkillChipPlayback.js`의 연속 전투용 순차 그룹 처리는 선행 행동과 KO·증원을 마친 뒤 다음 그룹을 재생한다. 이전 몬스터의 탄착이 새 몬스터에 넘어가지 않으며 하나의 스킬 시계와 이펙트 수명을 유지한다.
- 준비·일시정지와 재개는 같은 시계를 사용한다. 완료 알림은 일반 공격·스킬칩·증원 모두 실제 처리 후 한 번씩 전달한다. 취소한 전투의 후속 이벤트는 실행하지 않는다.
- PixiJS·GSAP 공용 구현과 잠금 의존성을 그대로 사용한다. 9개 기존 소비자 번들만 다시 빌드하며 승인 원화·SD·스킬 프레임·오디오는 변경하지 않는다.

## 검증

- 배틀슈트와 두 스킬칩을 장착한 동일 서버 기록으로 수정 전 지연 경고를 재현하고 수정 후 전체 순서를 대조했다.
- 폐차장: 서버 134개 이벤트 전부 동일 순서, 10체 격파, 스킬칩 3회 발동, 종료 시 남은 탄착·이펙트 0.
- 무한의탑: 서버 330개 이벤트 전부 동일 순서, 28체 격파, 스킬칩 9회 발동, 종료 시 남은 탄착·이펙트 0.
- 미장착 일반 덱: 폐차장 74개·탑 179개 이벤트를 끝까지 재생하고 기존 결과 화면에 도달했다.
- 스킬칩 없이 M200 배틀슈트 장착: 폐차장 68개·탑 172개 이벤트를 끝까지 재생했다. 긴 발사 간격에서도 탄착 대기 경고와 잔여 큐가 없다.
- 모바일에서 일시정지 중 결과 보기로 취소한 뒤 같은 렌더러로 다시 시작했다. 취소한 전투의 이벤트가 추가로 실행되지 않았고 새 전투의 134개 이벤트가 모두 완료됐다.
- 데스크톱 1440×1080·모바일 390×844에서 실제 운영 진입 화면을 통해 재생하고 일시정지·재개를 확인했다. 검수 계정은 별도 로컬 SQLite이며 운영 계정의 입장권·재화를 사용하지 않는다.
- 실제 연속 엔진의 단일 시계, 15초 이후 이벤트, KO 대기 중 후속 탄착 차단, 정지 중 취소, 공용 브리지 전체 타임라인 전달을 회귀 테스트에 추가했다.

## 배포 범위

운영 UI·층·보상·입장권·CMS 정책·개방 플래그·피해 계산은 그대로다. `2095-combat-clock`, 공용 번들 `105-continuous-clock`, 브리지 `3.35.0-continuous-clock`으로 캐시를 갱신한다. 진행 중 탑 기록의 저장 키 `cnine:tower:battle:v2094`를 유지하므로 갱신 후에도 받은 전투 기록을 복구할 수 있다.

배포는 범위 커밋 후 `npm run deploy:production`의 전체 `release:gate`를 통과한 후보만 사용한다.

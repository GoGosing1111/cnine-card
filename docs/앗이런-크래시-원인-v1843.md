# "앗, 이런!" 간헐적 크래시 — 원인 분석

`앗, 이런!` 은 크롬 **렌더러 프로세스가 강제 종료**될 때 뜨는 화면입니다.
JS 에러가 아니라 프로세스가 죽은 것이고, 모바일에서 대부분 **메모리 고갈**입니다.

먼저 아닌 것부터 지웠습니다.

| 후보 | 확인 결과 |
|---|---|
| 전투 응답(JSON) 과다 | 15~36KB. 무관 |
| PixiJS 렌더러 누수 | 생성 6 / 파괴 6 — 균형 |
| WebGL 컨텍스트 누적 | 모달 닫을 때 `destroy()` 호출됨 |
| 서비스워커 캐시 폭주 | 런타임 캐시. 프리캐시 아님 |
| 도감/덱 목록 | 가상화 O — `materialize`/`unmaterialize` 양방향 |

남은 하나가 원인입니다.

---

## 원인 — 100연차 뽑기 결과 모달

`js/app.js` 결과 모달은 **뽑은 카드를 전부 한 번에 DOM 에 올립니다.**

```js
<div class="result-grid count-${count}">${results.map(...)}</div>   // count = 100
```

그리고 결과 카드는 **반응형 축소본을 쓰지 않습니다.**

```js
// cardHtml
const iconCard = deckCard || dexCard;                    // result-card 는 여기 없음
responsiveCardImageMarkup(card, { enabled: iconCard, ... })
//                                        ↑ false → 원본 <img src> 그대로
```

### 브라우저가 실제로 먹는 메모리

이미지 메모리는 **파일 크기가 아니라 `가로 × 세로 × 4바이트`** 입니다.
0.2MB 짜리 webp 도 2048×1536 이면 디코딩하면 12MB 입니다.

카드 원본 2,097장 실측:

```
중앙값  0.9 MB     평균 1.6 MB     상위10%  3.5 MB     최대 22.1 MB
```

| 동시 표시 | 평균 카드로 | 상위 10% 카드로 |
|---:|---:|---:|
| 10장 | 16 MB | 35 MB |
| 20장 | 32 MB | 71 MB |
| **100장** | **160 MB** | **354 MB** |
| 200장 | 320 MB | 708 MB |

**모바일 크롬 렌더러는 보통 300~500MB 에서 죽습니다.**

여기에 PixiJS 번들(810KB), app.js(542KB), 카드 1장당 최대 6개의 프레임·배지
이미지가 더 얹힙니다.

### 왜 "간헐적" 인가

세 가지가 겹쳐야 터집니다 — 그래서 재현이 안 됩니다.

1. **100연차를 돌렸는가** (20연차는 32MB 라 안전)
2. **무거운 카드가 걸렸는가** — 같은 100장이라도 160MB 일 수도, 354MB 일 수도
3. **기기에 여유 메모리가 있었는가** — 저가/구형 안드로이드일수록 빨리 죽음

**자동 뽑기(`autoDrawState.targetRuns`)** 는 100연차를 반복합니다.
회차마다 새 카드 100장이 디코딩되면서 압력이 계속 쌓입니다.

### 표시 크기와의 격차

```css
.result-grid { grid-template-columns: repeat(5,1fr) }
@media(max-width:767px){ .result-grid { grid-template-columns: repeat(2,1fr) } }
```

400px 폰에서 카드 한 칸은 **약 190px**. 거기에 **2048px 원본**을 넣고 있습니다.
픽셀 면적 기준 약 **115배** 낭비입니다.

## 왜 반응형 축소본이 안 걸리나

파이프라인은 이미 있습니다 (`scripts/generate-responsive-card-images.py`).
문제는 **커버리지**입니다.

```
매니페스트 등록:  337장   (js/responsive-card-images-v1729.js)
assets/cards 실제: 2,243장
→ 1,906장이 원본 그대로 나갑니다
```

스크립트가 `--input` 으로 **그 시점의 활성 카드 목록**을 받아 돌린 뒤,
카드가 늘어나는 동안 다시 안 돌린 상태입니다.

즉 결과 모달뿐 아니라 **도감·덱 편성도 85% 는 원본을 씁니다.**

## 조치 — 두 갈래

### A. 반응형 이미지 재생성 (코드 변경 0, 효과 큼)

`scripts/반응형-카드이미지-재생성.md` 에 SQL·명령어까지 적어뒀습니다.
384px 축소본은 디코딩 **0.8MB** 라, 100장 기준 **160~354MB → 약 79MB** 로 내려갑니다.

> ⚠ 끝나면 `index.html` 의 `responsive-card-images-v1729.js?v=` 를 꼭 올리세요.
> `_headers` 가 `/js/*` 를 1년 immutable 로 잠급니다.

### B. ~~결과 모달에서 화면 밖 카드 이미지를 내리기~~ → **실측 후 기각**

처음에 제안했다가 헤드리스 크롬으로 재보고 **철회했습니다.**

| 방식 | 크롬 전체 RSS 증가분 (무거운 카드 100장 · 3회 중앙값) |
|---|---:|
| 현재 — 원본 100장 | **+417 MB** |
| A — 384px 축소본 | **+56 MB** |
| B — 원본 + 화면 밖 `src` 제거 | +379 MB |

B 는 9% 밖에 안 줄고, 스크롤을 되돌리면 같은 이미지를 재디코딩해 오히려 더 쓰는
구간이 나왔습니다. 결과 카드에는 이미 `loading="lazy"` 가 걸려 있어 크롬이 알아서
지연 로드하고, **화면에 들어오는 순간 원본 해상도로 디코딩되는 건 똑같기** 때문입니다.

**메모리를 줄이는 방법은 애초에 작은 이미지를 디코딩하게 하는 것뿐 — A 입니다.**

### 측정 방법

헤드리스 크로미움(뷰포트 400×700), 실제 카드 이미지, 결과 그리드 100장,
끝까지 스크롤하며 크롬 전체 프로세스 RSS 최대치를 측정. 각 3회 반복.
`assets/cards` 에서 디코딩 메모리 상위 100장을 골라 최악 상황을 재현했습니다
(무작위 100장은 +35MB 로 안전 — 이게 "간헐적" 인 이유입니다).

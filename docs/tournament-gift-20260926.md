# 대회 사은품 — 2026-09-26

사용자 요청으로 `TOURNAMENT_GIFT_BOX`(대회 사은품)를 즉시 지급·개봉 가능한 인벤토리 아이템으로 추가한다. 상자 1개당 마스터의 별 **2,000,000개**와 **250,000,000,000 코인(2,500억)**을 둘 다 확정 지급한다. 무작위 보상·추가 비용은 없다.

## 사용·지급

- CMS → 유저 관리 → 대상 계정 관리 → 인벤토리 아이템 지급 → **대회 사은품**. 기존 1~9,999개 지급 범위를 사용한다. 지급 확인창에 대상·수량·개봉 보상을 표시한다.
- 유저 인벤토리 → 팩·상자 → 대회 사은품 → 아이템 개봉. 한 번에 1개 개봉하며 보상 확인·수령 완료 화면에 두 보상을 함께 표시한다.
- 수신자가 지정되지 않았으므로 이번 작업에서 운영 계정에 실제 상자를 지급하지 않는다. 판매·드랍·메시지 보상 목록에 자동 편입하지 않는다.

## 서버·재시도

- `_tournament_gift.js`는 기존 `joint_operations_v1` 영수증과 `joint_atomic_guards_v1`, `DB.batch`를 재사용한다. 공통 트랜잭션 기반·DB 스키마·인증·경제 상한을 변경하지 않는다.
- PostgreSQL 사용자 행 잠금 안에서 상자 1개 차감, 별 지급, 코인 지급, 모든 감사 로그와 완료 기록을 함께 확정한다. 실패 시 전체 롤백한다. 지급 또한 기존 유저 관리 권한과 대상 계정 잠금 안에서 수량·로그·영수증을 원자적으로 반영한다.
- 개봉/지급 요청 ID, 대상, 관리자, 수량, 사유를 영수증에서 검증한다. 같은 요청은 재지급하지 않으며 다른 내용으로 재사용할 수 없다. 응답 유실 후에도 같은 ID로 복구한다.
- 브라우저가 미완료 개봉 ID를 계정별로 보관한다. 마지막 상자가 이미 소모된 상태에서도 인벤토리 재진입 시 이전 결과 확인창을 연다. 지급 완료 후 프로필 새로고침 실패를 개봉 실패로 표시하지 않는다.
- 카탈로그 등록은 `tournament_gift_catalog_20260926` 독립 마커를 사용한다. 기존 foundation 마커가 있어도 inventory 조회·관리자 지급·개봉 경로에서 등록된다. 이후 CMS 수정·비활성화는 덮어쓰지 않는다. 등록 마커만 30분 캐시하며 잔액은 캐시하지 않는다.

## 검증·배포 범위

- 변경 규모: 단일 인벤토리 보상 아이템. 기존 거래 기반을 재사용하며 인증·DB 마이그레이션·의존성 변경 없음. 지정 scoped 배포를 사용한다.
- 관련 회귀: `tests/tournament-gift-20260926.test.mjs`. 실제 PGlite PostgreSQL과 운영 DB 호환 어댑터로 정확한 큰 정수 보상, 0개·잘못된 수량, 동일/서로 다른 동시 요청, 요청 소유권, 감사/별/완료 기록 오류 롤백, 동일 ID 재시도, 커밋 응답 유실, CMS 비활성 상태, 숫자 범위, 기존 foundation 등록을 검사한다.
- 개발 단계 회귀 8개 통과. 따뜻한 카탈로그의 개봉 SQL은 25개로 고정되고 거래 batch는 1회다. 로컬 WASM 측정은 24ms였으며 운영 지연·부하 측정값은 아니다. 계정·아이템 기본키와 영수증 기본키를 조회하며 전 계정 스캔·아이템별 반복 조회를 추가하지 않는다.
- UI: 운영 인벤토리/관리자 함수·마크업을 사용한 API fixture에서 1440×980, 390×844, 320×650 검수. 인벤토리 선택→개봉→결과→복귀, 관리자 선택→수량→지급, 응답 유실·잔여 0개 복구, 결과 후 프로필 갱신 실패를 확인했다. 가로 넘침·페이지 JS 오류 없음. 실제 운영 계정 재화는 사용하지 않았다.
- 최종 배포는 `SCOPED_DEPLOY_TESTS=["tests/tournament-gift-20260926.test.mjs"]`, `SCOPED_DEPLOY_CHECKS=[]`와 `npm run deploy:production -- --scoped`로 진행한다. Worker 컴파일·출시 플래그·캐시·Hyperdrive 검사는 지정 도구에 맡긴다. 직전 운영 기준과 결과는 아래에 기록한다.

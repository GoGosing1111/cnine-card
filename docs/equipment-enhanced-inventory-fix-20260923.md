# 장비 강화 목록·중복 개체 장착 수정 (2026-09-23)

## 원인과 수정

- 강화 센터는 최근 획득 40개부터 읽어 오래된 소버린·미스틱이 뒤로 밀렸다. 전체 보유 장비의 **강화 반영 전투력 내림차순 / 동률 개체 ID 내림차순**으로 커서를 변경했다. 기존 개별 장비 선택과 부위 필터는 유지한다.
- 일반 장비창은 종류당 장착 중 개체 하나를 대표로 선택해 다른 개체의 강화 상태가 숨겨졌다. 같은 종류라도 **강화 단계별 묶음**으로 분리한다. 각 묶음은 실제 소유 개체 ID를 사용하고, 같은 단계에서는 현재 장착 개체를 보존한다. 자동 장착이나 개체 병합·삭제는 하지 않는다.
- 일반 장비창의 개별 전투력에는 기본 수치만 전달되어 클라이언트 재계산 때 강화 보너스가 빠졌다. 강화된 total/PVE/PVP를 전달하며 이름에 +단계를 표시한다. 늦게 도착하는 종류별 총 수량은 강화 묶음 수량을 제외한 미강화 수량으로 계산하여 중복 합산하지 않는다.
- 강화 센터 카드에 현재 전투력과 정렬 기준을 표시하고, 일반 장비창의 오래된 ‘강화 오픈 준비’ 안내를 중립적인 ‘강화 · 보호 · 복구’로 바꾼다. 기능 ON/OFF는 기존 서버 정책을 따른다.

## 운영 읽기 전용 확인

- 소버린 SKS(id 31, WEAPON, 115000), 미스틱 4종(id 32~35, BOTTOM/SHOES/TOP/ACCESSORY, 각 50000)은 모두 MYTHIC·active=1·public=1이다. 미스틱 슈트는 강화 제외인 BATTLE_SUIT가 아니라 TOP이다.
- 운영의 `(user_id,equipment_id,id)` 인덱스를 확인했다. 종류별 LIMIT 41의 LATERAL 인덱스 조회 + 작은 강화 상태 집합을 합친다. 수백만 개 소유 장비 전체를 정렬하거나 전역 PK를 역순 스캔하지 않는다.
- Neon의 동일 후보 조회 EXPLAIN ANALYZE: 계정 1 약 30.643ms; 집계상 9,112,943개 보유 계정 4774 약 133ms. 이는 DB 조회 실측이며 브라우저/API 전체 응답시간을 의미하지 않는다.
- 다음 페이지는 카탈로그의 기본 전투력 상한과 개체 ID 인덱스 범위를 먼저 제한한다. 높은 전투력 종류를 이미 지난 페이지에서 해당 종류의 모든 복사본을 훑지 않는다.

## 검증

- PostgreSQL(PGlite)·SQLite: 83개 최근 저전투력 장비보다 오래된 소버린·미스틱이 먼저 표시됨, +10 반영으로 순위 역전, 페이지 크기 1/7/40/100 전체 순회에 중복·누락 없음, 부위 필터·타인 커서·비공개·배틀슈트 제외, 미스틱 4종/소버린의 일반 USER 강화 견적 허용.
- 같은 종류의 +0/+9/+10 묶음 분리, 같은 단계 2개 수량 집계, 장착 개체 유지, 전부 강화된 경우 +0 가짜 묶음 없음, 비동기 수량 중복 합산 없음.
- 실제 `handleEquipment` USER 장착 API 회귀: 미강화 개체를 장착한 상태에서 강화 개체 노출, 선택 장착 성공, 서버 PVE/PVP 상승, 재조회 유지, 배틀슈트 PVE 분리 유지.
- 공유 장비 UI의 VM 회귀: 강화 개체가 전투력순 맨 위, 강화 단계 표시, 장착 후 전투력·수량 유지.
- 격리 SQLite UI 검수(운영 계정 미소모): 소버린 +0(115000) → 별도 +9(207000) 장착, 새로고침 유지, 데스크톱·390px 모바일 장비창 및 강화 센터, 미스틱 방어구 필터, 가로 넘침 없음. 로컬 UI 어댑터와 실제 서버 API 회귀는 구분했다.
- 재현: `FORGE_READINESS_QA=1 FORGE_INVENTORY_QA=1 REPAIR_QA_PORT=8964 node scripts/qa-pingdu-repair-coupon.mjs`, `/__qa/loadout` 및 `/equipment-forge/`. Windows에서는 각 환경변수를 PowerShell로 설정한다. 모든 QA 데이터는 프로세스 내 격리 SQLite다.
- 관련 직접 회귀 48개 통과(공개/출시 준비/목록/클라이언트/장착 API). 새 테스트는 정규 `test:equipment-forge-public`에 포함했다.

## 배포 경계

운영 DB의 계정 장비·장착·재화·확률·비용·CMS ON 설정은 변경하지 않는다. DB 마이그레이션 불필요. `npm run deploy:production`의 전체 `release:gate` 통과 후 코드만 배포한다. 공개 모듈 및 지연 로딩 캐시 키를 갱신한다. 원복 시 이 변경의 코드만 되돌리고 강화 상태/기록/승인 정책은 그대로 보존한다.

# 유저관리 리페어권·장비 보호권 지급 — 2026-09-29

사용자 요청에 따라 `유저관리 → 상세 관리 → 인벤토리 아이템 지급`에 핑두 리페어권과 장비 보호권을 추가한다. 대상 계정의 현재 보유 수량을 표시하며 아이템·수량·사유를 입력해 인벤토리에 직접 지급한다. 수량 범위는 기존 관리자 인벤토리 지급과 같은 1~9,999장이다.

## 변경 범위

- 관리자 화면의 두 아이템 선택, 대상·아이템·수량 확인 문구, 지급 후 보유 수량 표시와 모바일 입력 배치.
- 기존 `admin/users/action`의 `INVENTORY` 분기에 전용 지급 처리를 연결한다. `USER_MANAGE`와 non-OWNER의 OWNER 대상 차단은 기존 경로를 사용한다.
- 기존 사용자 변경 잠금과 공동 트랜잭션을 이용해 인벤토리, 인벤토리 기록, 관리자 기록을 함께 저장한다. 응답 유실 후 동일 요청 재시도는 한 번만 지급하며 요청 번호로 계정·관리자·아이템·수량·사유를 바꿀 수 없다.
- 기존 카탈로그를 사용하고 비활성 아이템은 지급하지 않는다. 신규 스키마·의존성·공통 인증·트랜잭션 기반·출시 플래그는 변경하지 않는다.
- 관리자 HTML의 JS/CSS 캐시 키는 `forgeTickets=20260929`다.

## 관련 검증

- `node --test tests/admin-forge-ticket-grant-20260929.test.mjs`: 8개 통과. 두 지급 경로, 기존 권한 조건, 입력 오류·비활성 카탈로그, 동일 요청 재사용·변조, 로그/완료 저장 실패 롤백, 응답 유실·동시 재시도, 정수 오버플로와 UI 요청 번호 재사용을 확인했다.
- 테스트는 격리 PGlite와 운영 Postgres 호환 래퍼 및 실제 API의 지급 분기를 사용한다. 첫 지급 SQL은 리페어권 27문/보호권 25문이며 운영 지연 시간 측정은 아니다.
- PC 1440px에서 리페어권 3장 지급과 보유 수량 갱신을 확인했다. 390px 모바일 프레임에서는 두 입력을 세로 배치해 아이템 이름이 잘리지 않음을 확인하고 장비 보호권 2장 지급 및 지급 기록을 확인했다. 모두 격리 검수 계정이며 운영 지급은 발생하지 않는다.
- `git diff --check` 통과. Worker 컴파일과 출시 보호 검사는 지정 scoped 배포 과정에서 실행한다.

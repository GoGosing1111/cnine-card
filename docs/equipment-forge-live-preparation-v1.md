# 장비 강화 V2 라이브 업데이트 준비

2026-09-12 사용자 지시: **장비 프리뷰 해당 UI,연출 최종 승인 라이브 업데이트 준비할것**.

같은 날 후속 선공개 지시로 `equipment-forge/`와 OWNER CMS, 보유 인스턴스 읽기 API를 연결했다. 무기·상의·하의·신발·장신구를 지원하며 강화·복구는 OFF다. 현재 선공개 상태는 `docs/equipment-forge-public-v2084.md`가 우선한다. 아래 실행 설계와 미정 정책은 준비 상태를 유지한다.

## 완료 범위

V2의 UI·색감·레이아웃과 성공·유지·파괴·보호·복구 연출은 최종 승인됐다. 승인받은 HTML/CSS·연출 코드·생성 이미지·무기 원본·현재 음원 믹스·공유 런타임을 22개 파일의 SHA-256으로 고정했다. 단일 기준은 `preview/equipment-forge-v1/release/approval.json`이며 프리뷰 소스 커밋은 `19bdc5c5`다. V1 반려본은 복원하지 않는다.

이미지·음원은 원본 바이트를 검증한다. 텍스트 파일은 Windows/Git 체크아웃 개행 차이만 LF로 정규화해 검증하며 파일 자체는 변환하지 않는다. 현재 프리뷰의 음원 믹스·게인·타이밍에 대한 승인을 다른 전투 연출의 승인으로 확대하지 않는다.

화면은 승인본 그대로 유지한다. 2026-09-12 후속 승인으로 장비 강화 전투력 기준을 확정하고 `release/launch-draft.json`의 `policy.powerScaling`에 기록했다. 단계별 확률·비용·보호권 소모·복구 정책은 미정이며 `liveEnabled=false`를 유지한다. 승인 수치는 `docs/equipment-mercenary-power-approved-20260912.md`가 기준이고 현재 계정 전투력에는 적용하지 않는다.

| 준비 항목 | 결과 |

## 운영 구조 확인

검토한 운영 기준은 `1257409e6e14c6d77dec7e7954916985d2be96b0`이다. `functions/_equipment.js`와 `js/equipment-v1274.js`는 현재 작업 트리와 동일했다.

- `character_equipment_items`: 장비 종류·공개 여부·기본 PVE/PVP 전투력.
- `user_equipment_instances`: 실제 개별 소유 인스턴스. 기존 컬럼에는 강화 단계·파괴 상태·상태 버전이 없다.
- `user_equipment_loadout`: 계정·슬롯에 실제 `instance_id`를 연결한다.
- 기존 `character/loadout`은 같은 종류를 묶어 대표 인스턴스와 `quantity`를 반환한다. 대표 ID를 보유 수량만큼 복제하거나, 같은 종류 전체에 강화 단계를 적용하면 안 된다.
- 현재 전투력은 카탈로그와 장착 정보를 읽는다. 강화 상태를 추가하는 것만으로 실제 전투력이 바뀌지 않는다.

준비 함수 `readForgePreparationInventory(db, authenticatedUserId, { beforeId, limit })`는 개별 인스턴스를 ID 내림차순으로 조회한다. 계정 소유·활성·공개 상태를 확인하고, 장착 여부를 계정까지 일치시켜 읽는다. 기본 40개·최대 100개씩 조회해 대량 중복 장비도 한 번에 내려받지 않는다. 계정 ID는 인증 결과에서 전달해야 하며 요청 본문의 계정 ID를 신뢰하지 않는다. 이 함수 자체는 인증 라우트가 아니다.

## 운영 연결 순서

1. **정책 확정:** 최대 단계, 단계별 3종 확률, 장비/등급/배틀슈트 대상, 비용·차감, 실제 전투력, 보호권 소모·게임 내 희귀 획득 수치, 복구 대상·기간·단계·쿠폰·재파괴·재료 반환 규칙. 사용자 지정 10% 하한·상자 제외는 고정이다. `model.mjs`의 +15·6%·코인·결정 수치를 자동 승계하지 않는다.
2. **상태·영수증 스키마:** 개별 장비 ID에 강화 단계와 변경 버전을 연결한다. 파괴 기록은 원래 인스턴스·장비 종류·단계·정책 버전·파괴 시각을 보존한다. 요청 영수증은 계정+요청 ID에 유일해야 하며 복구 기록의 1회 사용을 DB에서 제한한다. 스키마 변경은 아직 수행하지 않았다.
3. **서버 견적:** 인증된 사용자와 인스턴스를 확인하고 비용·확률·실제 전투력 비교·보호/복구 적격 여부를 서버에서 산출한다. 견적 ID·정책 버전·인스턴스 버전·만료를 함께 반환한다.
4. **원자적 강화:** 계정·인스턴스·정책·견적·소유/거래/진행 상태를 잠그고 확인한다. 서버 CSPRNG로 한 번만 추첨한 뒤 재료 차감·장비 변경·파괴 기록·장착 해제·영수증을 하나의 트랜잭션으로 커밋한다. 조건부 UPDATE/INSERT/DELETE가 기대 행수와 다르면 전체 롤백한다. 클라이언트 추첨 값·금액·보호 처리 결과를 받지 않는다.
5. **원자적 복구:** 기록 소유·적격 기간·미사용 상태·쿠폰·같은 장비 복구 가능 상태를 재검증한다. 복구 지급이 0행이면 쿠폰과 기록을 소비하지 않는다. 동시 요청과 중복 요청을 DB 유일 제약·잠금·영수증으로 처리한다. 복구 시 자동 장착 여부는 정책 확정 전 추정하지 않는다.
6. **기존 기능 통합:** 장착/해제·합성/소모·관리자 회수와 같은 인스턴스 잠금 규칙을 공유한다. 강화 단계가 다른 동일 장비를 현재 묶음 표시가 숨기지 않도록 장비 목록을 연결하고, `userEquipmentBonuses`·배틀슈트·서버 전투 스냅샷이 확정 전투력을 읽게 한다. 기존 완료 전투의 판정은 바꾸지 않는다.
7. **UI 연결:** 승인 CSS·원본 자산·`ForgeFX`·`SuccessCinematic`과 공용 PixiJS/GSAP을 재사용한다. 운영 호스트에는 프리뷰 추첨·확률 편집·초기화·연출 시연·가상 보유량을 넣지 않는다. 실제 서버 견적과 영수증으로 승인 레이아웃을 채우고, 결과 저장 이후에 연출을 재생한다. 연출 실패·건너뛰기·화면 이탈로 서버 판정을 되돌리거나 재시도하지 않는다.
8. **CMS·획득·검수:** 운영 정책 버전·유효기간·획득 콘텐츠를 명시적으로 저장한다. 보호권이 기존 상자·블랙미라클·프라임 풀에 자동 편입되지 않는지 확인한다. 실제 계정 스냅샷, 큰 보유 수량, 다른 계정, 동시 요청, 0행 지급, 재파괴, 응답 유실·재접속, 모바일·WebGL 실패를 검수한다.
9. **배포:** 정책 확정과 실제 연결·활성화 지시가 충족되면 깨끗한 최신 main 기반 배포 후보에서 `npm run release:gate`를 통과하고 `npm run deploy:production`만 실행한다. 이번 준비 커밋이나 UI 승인은 다른 콘텐츠 출시 조건을 해제하지 않는다.

## 제안 API 계약

아래 경로는 실행 준비 계약이다. 후속 v2084에서 `state`를 읽기 전용으로 연결했고, `quote/enhance/restore/receipt`에는 OFF 차단 응답만 연결했다. 실제 견적·강화·복구·영수증 기능은 아직 구현되지 않았다. 기존 인증·재화·DB 계층을 재사용한다.

| 경로 | 역할 |
| --- | --- |
| `GET character/equipment/forge/state` | 개별 인스턴스·확정 정책·재료·복구 이력·페이지 커서 |
| `POST character/equipment/forge/quote` | 장비/기록의 서버 견적과 상태 버전 |
| `POST character/equipment/forge/enhance` | 견적에 따른 한 번의 서버 강화 |
| `POST character/equipment/forge/restore` | 파괴 기록에 따른 한 번의 서버 복구 |
| `GET character/equipment/forge/receipt?requestId=...` | 응답 유실·재접속 시 처리 결과 복구 |

`release/server-receipt.mjs`의 `createCommand`는 `instanceId`, `quoteId`, `policyRevision`, `expectedInstanceVersion`, `requestId`, 강화 시 `useProtection`, 복구 시 `recordId`만 받는다. 숫자 ID는 문자열로 전달해 큰 정수 손실을 방지한다. 계정 ID·확률·비용·추첨 값은 요청 본문에 포함하지 않는다.

완료 영수증은 `schemaVersion:1`, `authority:'SERVER'`, `status:'COMPLETED'`, 인증 계정·요청·종류·정책 버전과 `before`/`after`를 포함한다. 장비 스냅샷은 개별 인스턴스·장비 종류·이름·안전한 이미지 경로·등급·단계·보유 상태를 명시한다. 서버의 `outcome:'destroy'`와 `protectionApplied:true`가 함께 있을 때만 보호 연출로 바꾸며 새로운 추첨 결과를 만들지 않는다. 복구 단계는 서버가 정한 `after.level`을 사용한다.

`authority`는 응답 형식 표기이며 인증 증명이 아니다. 인증·소유 검증·확률/비용 권한·중복 차감 방지는 반드시 서버와 DB가 강제해야 한다. 준비 수신 모듈의 `pending`은 메모리 범위다. 새로고침·로그아웃·재접속 복구는 계정별 미결 요청을 서버에서 조회하는 실제 호스트 연결과 함께 구현한다. 자동 재추첨으로 대신하지 않는다.

## 검증 진입점

```powershell
node --test preview/equipment-forge-v1/qa.test.mjs preview/equipment-forge-v1/release/qa.test.mjs
node preview/equipment-forge-v1/release/check.mjs
```

마지막 명령은 현재 출시 미준비 상태를 검출해 종료 코드 1을 반환해야 한다. 승인 화면의 HTML/CSS와 시각 연출 파일을 변경하지 않았으므로 기존 시각 검수 20개와 승인 원본 해시를 유지하고, 이번 변경은 실제 PostgreSQL 조회 및 계약·중복·복구 실패 경로를 추가 검수한다.

2026-09-12 결과: 기존 20개+신규 11개 **31/31 통과**. PostgreSQL(PGlite+프로젝트 DB 호환 계층)에서 같은 종류의 3개 인스턴스 분리·페이지 이동·다른 계정·비공개/비활성 장비 제외·장착 일치·기존 50억 코인/장착/인스턴스 보존을 확인했다. 준비 검사 오류 0개, 원본 22개 일치, 실제 출시 검사 차단은 정상이다. 운영 DB 조회·스키마 변경·재화 변경·배포는 실행하지 않았다.

PATCH-NOTES-v1790 : D1 읽기 복제(Sessions API) 도입

[배경]
v1784~v1786 으로 쓰기 병목(유저 뮤텍스 락)은 제거했다.
남은 벽은 읽기다. withSession 사용처가 0건이라 모든 조회가
단일 프라이머리 인스턴스로 몰리고 있었다.
이 워크로드는 읽기가 압도적으로 많아 여기서 가장 큰 여유가 나온다.


[핵심 아이디어]
D1 세션 객체는 env.DB 와 동일한 prepare/batch 인터페이스를 가진다.
따라서 요청 시작 시 세션을 하나 만들어 env.DB 자리에 끼워 넣으면
기존 1,400여 개 쿼리를 한 줄도 고치지 않고 전부 복제본 경로를 타게 된다.
쓰기는 Sessions API 가 알아서 프라이머리로 보낸다.


[수정] functions/api/[[path]].js

1. startD1Session(env, request) 추가
   요청 성격에 따라 일관성 제약을 고른다.

     변경 요청(GET 이 아닌 것)  → 'first-primary'
       전투 에너지 차감, 재화 검사처럼 "읽고 판단해서 쓰는" 흐름이 많다.
       복제 지연이 끼면 이중 지급·이중 차감이 날 수 있으므로 안전을 택한다.
       (읽기 분산 이득을 일부 포기하는 대신 정합성을 지킨다)

     조회 요청(GET)             → 클라이언트가 돌려준 북마크
       북마크는 "최소 이만큼은 최신인 복제본" 을 보장한다.
       방금 쓴 결과를 못 보는 read-your-writes 위반이 생기지 않는다.
       북마크가 없으면 'first-unconstrained' (아무 복제본이나).

2. onRequest 에서 env.DB 를 세션으로 교체
     const {db:sessionDb,session:d1Session}=startD1Session(context.env,request);
     const env=sessionDb?{...context.env,DB:sessionDb}:context.env;
     context={...context,env,waitUntil:...bind(context)};
   context 까지 갈아끼워 handleRequest 내부 전체에 전파한다.
   waitUntil 은 bind 해서 보존한다 (v1785 deferWrite 가 이걸 쓴다).

3. 응답에 x-cnine-d1-bookmark 헤더 반환
   CORS allow-headers / expose-headers 에도 추가.

4. 폴백
   withSession 이 없거나 예외를 던지면 기존 env.DB 를 그대로 쓴다.
   즉 읽기 복제를 켜지 않은 상태로 배포해도 동작이 바뀌지 않는다.


[수정] js/app.js
   apiRequest 가 북마크를 왕복시킨다.
   - 요청: 저장된 북마크를 x-cnine-d1-bookmark 헤더로 전송
   - 응답: 헤더에서 북마크를 읽어 보관 (본문 파싱보다 먼저 → 실패 응답에서도 갱신)
   메모리에만 둔다. 새로고침하면 초기화되는데,
   그때는 북마크 없이 시작하므로 안전 쪽으로 동작한다.


[운영 작업 — 이걸 해야 실제 효과가 난다]
Cloudflare 대시보드 → D1 → cnine-card-db → Settings → Enable Read Replication

  - 이 토글을 켜기 전까지는 코드가 배포돼 있어도 읽기가 계속 프라이머리로 간다.
    (동작은 정상, 이득만 없음)
  - 추가 비용 없음. 복제본에 대한 별도 스토리지/컴퓨트 과금이 없고
    과금은 종전대로 읽은 행 수 / 쓴 행 수 기준이다.
  - 되돌리려면 토글만 끄면 된다. 코드는 그대로 두어도 된다.


[버전 갱신]
  - index.html        app.js?v=1790-d1-read-replication
  - service-worker.js SHELL_CACHE → soop-card-shell-v1790-d1-read-replication


[검증] verify-1790 7종 통과
  1 변경 요청(POST/PATCH/PUT/DELETE)은 first-primary
  2 조회 요청은 북마크 기반, 없으면 first-unconstrained, 공백 북마크 무시
  3 withSession 미지원 / 예외 / env 부재 → 기존 동작으로 폴백
  4 env.DB → 세션 교체 + context 전파 + waitUntil 보존
  5 응답 북마크 반환 + CORS 허용/노출
  6 클라이언트 북마크 왕복 (저장이 본문 파싱보다 앞섬)
  7 v1784/v1785 최적화 유지

  회귀: v1784 / v1785 / v1787 / v1788 스위트 전부 재실행 통과


[배포 후 확인]
  1. 토글 켜기 전 배포 → 게임이 평소대로 동작하는지 (폴백 확인)
  2. 응답 헤더에 x-cnine-d1-bookmark 가 붙는지 (DevTools Network)
  3. 토글 켠 뒤 →
     - 전투 후 코인/카드가 즉시 반영되는지 (read-your-writes 확인, 가장 중요)
     - api_timing 의 durationMs 분포가 내려갔는지
     - D1 대시보드에서 복제본 쪽 읽기가 잡히는지


[알아둘 것]
변경 요청을 first-primary 로 묶었기 때문에 POST 계열은 이번 작업의 이득을 받지 못한다.
전투 요청 자체를 더 빠르게 하려면 별도 작업이 필요하다
(profile() 다이어트, battle/fight 내부 조회 축소 등).
이번 작업의 이득은 조회 트래픽(목록·상태·폴링)에서 나온다.

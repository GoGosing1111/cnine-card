PATCH-NOTES-v1795 : 뽑기 "느리다 / 안 된다" 원인 제거

[제보]
뽑기(카드·장비·이동수단)가 느리고 안 된다는 문의가 계속됨.
카드가 안 들어온다는 문의는 없음 → 지급 로직이 아니라 "요청이 거부되거나 지연"되는 문제.
D1 에 영수증이 계속 쌓이고 DB 가 느려짐.

[조사 결과 — 뽑기 쿼리 자체는 이미 최적화되어 있었다]
draw 핸들러는 이미
  - 카드 조회를 json_each 로 벌크 처리 (N회 조회 아님)
  - user_cards 를 다중 VALUES 로 한 번에 INSERT
  - env.DB.batch 사용
하고 있다. 여기는 손댈 곳이 아니었다.


================================================================
문제 1. 락 유효기간과 영수증 회수 기준이 어긋나 있었다  ← "안 된다"의 원인
================================================================

  draw_active_lock_v1480 리스        : 120초 (2분)
  PENDING 영수증 회수 기준            : 600초 (10분)   ← 따로 박혀 있었음

2분이 지나면 그 요청을 처리하던 워커는 이미 없고 락도 자동으로 풀린다.
그런데 영수증 회수는 10분을 기다렸다.
결과: 2분~10분 구간에서 "락은 풀렸는데 영수증이 계속 409(DRAW_PENDING)를 내는"
      사각지대가 생긴다. 유저는 8분 동안 아무것도 할 수 없다.
      자동뽑기는 한 번 걸리면 세션 전체(최대 500회)가 그대로 멈춘다.

요청이 타임아웃되거나 INSERT 이후 상태 UPDATE 전에 실패하면 PENDING 이 남는데,
부하가 걸린 상황에서는 이게 자주 발생한다. 부하 → 타임아웃 → 8분 정지 →
문의 증가 → 재시도 폭주의 악순환.

[수정]
  const DRAW_ACTIVE_LOCK_LEASE_MS=120000;
  const DRAW_STALE_PENDING_MS=DRAW_ACTIVE_LOCK_LEASE_MS;   // 같은 상수에서 파생
매직넘버 120000 / 600000 을 전부 제거하고 사용처 3곳을 상수 파생으로 바꿨다.
두 값이 다시 어긋날 수 없다.

⚠️ 리스가 살아있는 동안(120초 이내)에는 여전히 회수하지 않는다.
   조기 회수로 중복 지급이 나면 안 되기 때문이며, 검증 3번이 이 경계를 확인한다.


================================================================
문제 2. 정리 작업이 쌓이는 속도를 못 따라갔다  ← "느리다 / 영수증이 쌓인다"의 원인
================================================================

  정리 태스크                 41개
  1회 처리량                  1개
  리스                        10분
  트리거 샘플링               요청 16,384건당 1회

한 바퀴 = 41 × 10분 = 410분 ≈ 6.8시간.
게다가 샘플링이 먼저 걸려야 하므로, 초당 27요청이 꾸준히 들어오지 않으면
그 6.8시간조차 지키지 못한다.

이 41개에는 draw_logs / coin_logs / shard_logs / battle_logs 등
뽑기가 많을수록 빠르게 쌓이는 테이블이 전부 들어 있다(보존 1일).
쌓이는 속도는 뽑기량에 비례하는데 정리 속도는 그렇지 않으니 계속 누적된다.

[수정]
  AUTO_STORAGE_MAINTENANCE_SAMPLE_MOD   16384 -> 512
  AUTO_STORAGE_MAINTENANCE_LEASE_MINUTES   10 -> 3   (신규 상수)
  AUTO_STORAGE_MAINTENANCE_TASKS_PER_RUN    1 -> 3   (신규 상수)

  한 바퀴 = ceil(41/3) × 3분 = 42분   (기존 410분 대비 약 10배)

부하 상한은 그대로다:
  - 리스 게이트 유지 (동시에 여러 워커가 정리하지 않는다)
  - 배치 상한 5000행 유지
  - 1회 부하 = DELETE 3건 × 최대 5000행
샘플링은 리스가 이미 상한을 잡고 있어 사실상 중복 방어였다. 그래서 낮춰도 안전하다.

커서는 처리한 태스크 수만큼 전진시키고 저장한다(같은 태스크 반복/누락 없음).
태스크별 결과를 runs 배열로 남겨 관리자 응답에서 확인할 수 있다.


[검증] verify-1795 6종 통과
  1 락 리스와 PENDING 회수 기준이 같은 상수에서 파생
  2 매직넘버 제거, 사용처 3곳 모두 상수 파생
  3 락 만료 후 즉시 회수 가능 / 리스 유효 중에는 보호 (조기 회수로 중복 지급 없음)
  4 정리 한 바퀴 410분 -> 42분
  5 리스 게이트와 배치 상한 유지 (부하 폭주 방지)
  6 커서가 처리 개수만큼 전진하고 저장됨
  회귀: v1784/1785/1787/1788/1790/1791/1792/1793 전부 통과


[배포 후 확인]
  1. 자동뽑기를 길게(100회 이상) 돌려서 중간에 멈추는지
     - 멈춘다면 어떤 code 로 멈추는지 확인 (DRAW_PENDING / DRAW_ALREADY_IN_PROGRESS /
       DRAW_OTHER_BROWSER_ACTIVE / D1_OVERLOADED)
  2. 관리자 admin/draw-performance (GET) 의 receiptsByStatus 가 줄어드는지
  3. 관리자 admin/storage-cleanup/summary (GET) 의 pages 가 더 이상 늘지 않는지
  4. 뽑기 응답 헤더 x-cnine-d1-queries (v1792 계측)


[아직 남은 것 — 다음 단계]
뽑기 1회당 D1 왕복이 여전히 14회 이상이다
(개별 prepare 11 + batch 3, 여기에 락 2회 쓰기 포함).
자동뽑기 500회면 7,000회가 된다.

  - draw_active_lock_v1480 / draw_browser_lease_v1480 을
    이미 운영 중인 USER_LOCK Durable Object 로 옮기면 뽑기당 D1 쓰기 2회가 사라진다.
    (전투에서 v1784~v1786 으로 이미 검증된 방식)
    다만 활성 락은 draw_request_receipts_v2 의 트리거로 해제되는 구조라
    모든 완료 경로에 명시적 해제를 넣어야 한다. 하나라도 놓치면
    "안 된다"가 더 심해지므로 이번에는 넣지 않았다.
  - 장비뽑기 / 이동수단뽑기 경로는 아직 같은 수준으로 분석하지 않았다.
    위 배포 후 확인 4번(계측 헤더)으로 실제 비용을 먼저 재는 것이 순서다.
